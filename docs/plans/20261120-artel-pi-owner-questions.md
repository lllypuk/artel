# Artel 4b: вопрос Pi и асинхронный ответ владельца

## Overview

- Из уже привязанной Pi-сессии агент явно задаёт вопрос по конкретной открытой задаче через инструмент расширения `artel_ask_owner`. Инструмент ждёт только сохранения вопроса, не ответа владельца. Владелец видит автора, задачу и формулировку в Qt, отвечает один раз и видит отдельно факт сохранения ответа и исход его доставки.
- Ответ поступает новым custom-сообщением в ту же Pi-сессию, когда та свободна. Он не перенаправляется при смене назначения и не отправляется повторно автоматически при неизвестном исходе. Сохранённые вопросы и ответы остаются читаемыми после закрытия задачи или отзыва допуска.
- Только локальный сценарий, один владелец и один допуск 4a. Нет глобального inbox, редактирования/TTL вопросов, рассылки, внешнего доступа, сбора диалогов, блокирующего ожидания в Pi, автоматических переходов задачи или разрешений на операции. Artel не исполняет команды и не выдаёт разрешений; новый ход Pi сохраняет обычные возможности своего runtime. Ответ не возвращается в результат исходного tool call.

## Solution Overview

- Выбран асинхронный инструмент Pi, а не ручная CLI-публикация и не удержание хода до ответа. Новая возможность явно включается владельцем у нового delivery-допуска, по умолчанию выключена; отдельный новый токен не нужен. Каналы и роли 4a не сливаются.
- Вопрос — неизменяемая запись с одним ответом. Ответ и постановка его в существующую очередь коммитятся одной транзакцией. Используется тот же `next → spend → verify → receipt`; второго механизма вызова Pi нет. Если ранний прогон показывает, что цепь 4a не держит этот контракт, остановиться и зафиксировать блокер, а не изобретать обход.

## Technical Details

### Допуск и совместимость

- Bootstrap: `artelctl delivery enable --allow-owner-questions`; бит входит в исходный запрос, replay и сверку при `--resume`, публикуется в подтверждённом конфиге и подтверждается daemon через delivery context. Отсутствующий бит — false; для false/absent сохранить прежние байты хешируемого enable/revoke и формат чтения receipts v3. При true поле обязательно уходит в enable: строгий старый daemon отвергает его без записи и CLI не публикует confirmed config. Не менять активный допуск на месте.
- Для opted-in допуска `attach` требует capability `owner_questions_v1` и атомарно фиксирует её за принятым writer ID (при замене writer сбрасывается/сверяется заново). Сервер проверяет зафиксированную capability и текущего writer до чтения ответа в `next`, до `spend` и `verify` ответа, а также до публикации вопроса. Запрос со случайно добавленным полем на позднем шаге не заменяет attach. При false/absent attach и wire обычных поручений сохраняют контракт 4a. Тестировать настоящий старый extension из базы, а не только отсутствие поля в новом клиенте.

### Записи, авторизация и повторы
- `POST /delivery/v1/questions`: авторизация delivery credential, сервер сверяет текущий writer, активный точный допуск, installation, runtime и Pi-session из доверенного контекста; задача открыта и принадлежит тому же проекту. Маршрут монтируется только на delivery UDS. Тело — `instance_id` из подтверждённого writer config, `task_id`, `writer_id`, `text`. В одной immediate-транзакции проверить ожидаемую БД, текущее назначение, writer, capability и принадлежность задачи, затем искать replay; открытость задачи/проекта обязательна для новой записи, но не для восстановления ACK при всё ещё действующем допуске. Ключ `Idempotency-Key` (UUID) scoped по операции `question.create` и допуску, канонический payload — instance/task/точный UTF-8 текст (writer проверяется при каждом вызове, не часть хеша). Совпавший payload возвращает исходный ID, несовпавший — конфликт. Устаревший допуск не получает историю. Новый tool call — новый запрос, не дедуплицировать по тексту и не генерировать повтор автоматически после рестарта. Возвращать только ID и факт сохранения; при неопределённом ACK сообщать неопределённость, не обещать запись.
- Owner API: `GET /v1/tasks/{task_id}/questions` с обязательным ожидаемым `instance_id` и двумя взаимоисключающими режимами: курсорная страница (`after`, `limit`) или обновление загруженных строк (`ids`, до 5 ID одной задачи). После owner auth сверить instance в той же read-транзакции до выборки; при несовпадении вернуть конфликт без строк или статусов. Qt отправляет instance из текущего snapshot в обоих режимах и не применяет ответ, если выбор или instance изменились за время запроса. Запись: `POST /v1/tasks/{task_id}/questions/{question_id}/answer` с `instance_id`, `text` и `Idempotency-Key`. Один ответ — ограничение в SQLite; пара конкурирующих POST даёт ровно одну запись ответа и одну строку очереди. Оба маршрута только в защищённом owner API. До replay проверить owner auth, ожидаемый instance и соответствие question → task из URL; ключ UUID scoped по `question.answer` и question ID, канонический payload — instance/task/question/точный UTF-8 текст. Точный replay возвращает подтверждение сохранения и ID, не актуальный статус доставки; несовместимый replay — конфликт. Перед новым ответом в той же транзакции проверить назначение и открытость задачи/проекта; readiness для сохранения не требуется. Не помещать текст вопроса/ответа в observer API, доменные events/SSE или логи.
- Владелец передаёт task UUID явно: Qt показывает доступный для копирования ID выбранной задачи, владелец передаёт его Pi в тексте поручения 4a или вручную в Pi. Не вводить поиск задач из инструмента и не снабжать Pi owner credential. В выбранной задаче Qt ограниченно опрашивает новые строки и обновляет уже загруженные по ID; временная ошибка или reconnect не сбрасывают черновик, поздний ответ и replay не откатывают подтверждённый `observed`.

### Жизненный цикл и доставка

- Закрытие задачи, архив проекта, явный `deliveryRevokeApply` и observer-driven `deliveryRevokeStaleBindings` атомарно закрывают затронутые unanswered questions и блокируют затронутые неотправленные 4b-ответы с сохраняемой причиной. Уже сохранённый ответ и `observed` остаются в истории. Если закрытие/отзыв коммитится первым, нового ответа нет; если первым коммитится ответ, его история сохраняется, а оставшаяся доставка блокируется. Reopen/unarchive и новый допуск старую очередь не открывают. Offline или остановка Pi сами по себе вопрос не закрывают: возможен ответ без readiness, но другой runtime не продолжает старый допуск, даже с тем же Pi-session ID. При подтверждённой смене назначения действуют правила отзыва; перенаправления нет.
- В очереди ответ имеет отдельный тип и `question_id`; все строки v3 мигрируют как поручения. Legacy `GET /v1/tasks/{task_id}/messages` (`ListDeliveryMessages`) отдаёт только поручения как в курсорном режиме, так и в режиме `ids`, включая запрос с ID ответа. `next` продолжает брать оба типа из общей очереди. Для ответа `next` возвращает связанный текст вопроса и ответа как данные, с идентификатором вопроса; Pi получает контекст в custom-сообщении, не как привилегированную инструкцию. Ограничить обе строки 4 КиБ UTF-8, отклонять пустые/невалидные строки и NUL. Установить отдельный лимит 32 КиБ для question POST и answer POST на клиенте и сервере (для UDS — как во входном фильтре, так и в декодере после выбора точного маршрута); observer остаётся на 16 КиБ. `next` — 64 КиБ; owner list — не более 5 строк и 320 КиБ на сервере и в Qt. Проверить реальный wire при шестибайтовом экранировании каждого допустимого байта и отказ до записи за пределами лимита. Ограничить глубину/форму JSON и метаданные; не логировать тела или токены.
- Состояния вопроса `open` / `answered` / `closed` не подменяют состояние доставки ответа. Доставка использует `stored` / `unknown` / `observed` и причину блокировки, как в 4a; `observed` означает только matching custom `before_agent_start`, не получение провайдером и не завершение. Закрытие/архив до verify блокирует выдачу разрешения на вызов; после verify не обещает отмены уже разрешённого вызова. При неизменном допуске его matching receipt может быть принят после закрытия/архива; после отзыва/смены первый receipt отвергается, ранее записанный `observed` сохраняется. Для ответа обработчик Pi требует customType `artel-owner-answer` и совпадение question/message/attempt/session с локальной попыткой до записи квитанции. Сервер может сохранить существующий receipt tuple, выводя kind/question из неизменяемой строки очереди. Сверять наличие и целостность исходного журнала до spend и перед синхронным гашением права/вызовом; отказ после spend оставляет `unknown`, повтор возможен только для уже сохранённой квитанции при том же текущем назначении и не вызывает Pi. После ответа задача не меняет статус.
