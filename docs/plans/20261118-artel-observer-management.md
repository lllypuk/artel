# Artel observer management: exact targets and confirmed cleanup

## Overview

Close the three known observer-management gaps left outside desktop PR #9: unbind identifies the actual binding, pending agterm lookup stops on invalidation, and prune retires only an exact set approved by the owner. This is a local single-owner MVP; the owner authorized changing the prune API and updating clients together. No rollout, production daemon/data access, automatic pruning, new agterm commands, or Pi control.

## Contract

- Unbind confirmation describes the captured bound runtime and project ID, regardless of clicked row, selected manual project or filters. A project name can supplement, never replace, the captured ID. Revalidate the captured binding directly against the current observer/database/binding and version/generation before sending, not by calling `prepare()` on the clicked row or comparing the manual project. Reserve manual-project identity checks for Bind, which still describes the selected project and proposed runtime.
- agterm lookup captures database instance, observer/runtime, binding version/generation and hint. Invalidate pending lookup on read/projection change that makes its target stale, revoked, replaced, or changes binding/hint. Mere heartbeats and filtering do not cancel a still-valid lookup. Revalidate just before dispatch (including time-based cache expiry even without a projection signal). After dispatch, do not claim an already issued command can be undone. Keep existing exact-session, window-scoped matching and no fallback/launch.
- Owner `POST /v1/observers/{observer_id}/prune` requires `expected_version` and `expected_runtime_ids` (JSON array of 1–8 unique canonical non-nil runtime UUID strings). Order does not matter. Missing, null, malformed, empty, duplicate or excess IDs return 400. Under the store transaction, calculate eligibility with the existing rule, compare the exact canonicalized set, and return existing HTTP 409 `version_conflict` on any mismatch **before** writes. No retired markers, partial deletion, version increment, audit or receipt on conflict. Validate request first, then look up receipts before CAS or eligibility. Prune hashes all existing request fields (including expected version) plus sorted IDs; same key and equivalent set replay the original result even after rows vanish, while different version or set conflicts. Preserve the exact pre-change hash encoding for provision, bind/unbind and revoke. A version-only legacy prune cannot replay after upgrade; reusing its key with an exact-set payload conflicts. Inspect the registry and prior result for an uncertain legacy outcome; do not blindly retry it as a new prune. Do not alter bound-runtime exclusions or storage limits.
- Expose server-computed `prune_eligible` on each runtime in the owner projection using the same predicate as the transaction, computed before the display disposition is overwritten for revoked observers. Update the OpenAPI and Qt sanitizer. If even one runtime lacks a boolean eligibility field, disable prune for the entire observer instead of constructing a partial set. Desktop shows the exact eligible IDs from the unfiltered sanitized registry for that observer, not just the clicked row. Explain permanent retirement, keep the bound runtime out, and don't offer empty prune. Capture and revalidate the full set by observer/database/version/generation, independent of the clicked row and selected manual project. Require refresh/reconfirmation on a known change; transaction check covers races after dispatch. CLI requires a repeatable explicit `--runtime-id UUID` for each confirmed ID, plus the existing `--id` and `--expected-version`; no automatic fetch-and-confirm. Document the upgrade and how to inspect candidates.
