# Artel / Pi, эксперимент №2: доставка и восстановление

Статус: изолированный эксперимент повторён; свидетельства и рекомендация — в [отчёте Task 4](../experiments/pi-bridge-delivery/evidence.md). Следующий продуктовый этап не запущен.

## Цель и границы

Этап 3 [дорожной карты](../roadmap.md). На фиктивных сообщениях выяснить, какие подтверждения Artel может честно показать владельцу и когда можно безопасно продолжить после сбоя. Проверить один маршрут: fake Artel → bridge → одна тестовая Pi-сессия. Исходящие вопросы, рабочий API/БД, Qt-интерфейс, реальные сессии, автоисполнение задач и подключение провайдеров вне машины не входят. Эксперимент не трогает рабочий `arteld`, реальные credentials, agterm или настройки пользователя.

Опора: [эксперимент №1](../architecture/20261117-artel-v2-pi-experiment-01.md), [его стенд](../experiments/pi-bridge/README.md) и существующий изолированный PTY-тест в `integrations/pi-observer/tests/`. Pi 1.5.2, Node 22.23.2; только публичные API, фиктивный loopback-провайдер, никаких инструментов и ресурсов проекта/пользователя внутри тестовой сессии. Не устанавливать зависимости на хост автоматически.

## Проверяемая гипотеза

Сервер хранит поручение отдельно от состояния доставки. Bridge перед обращением к Pi фиксирует устойчивый intent с идентичностью сообщения, назначения/поколения и сессии, а затем может записать наблюдённое свидетельство. Важное окно — после фиксации intent, до подтверждения: после рестарта намерение само по себе не доказывает, был ли вызов Pi. Состояние **«исход неизвестен»** блокирует автоматический повтор передачи. Потерянный ответ на запись квитанции можно восстанавливать повтором запроса с тем же ключом, не повтором вызова Pi. `sendMessage()` return, событие `message_end`, запись в истории, запрос к fixture-провайдеру и завершение задачи — разные границы. Ни одну не назвать гарантией exactly-once или устойчивости к отключению питания.

Fake API сохраняет сообщение и выдаёт идемпотентный допуск, который **не разрешает вызов Pi сам по себе**. Перед локальной записью попытки сервер атомарно расходует право вызова для `message_id`, проверив поколение, тестовую сессию и идентификатор текущего процесса-владельца. Только тот же процесс после получения исходного успешного ответа и фиксации локальной попытки может один раз вызвать Pi. Повтор запроса возвращает состояние, но не право на вызов; несовместимое тело конфликтует. Перезапуск, новый владелец или смена поколения не восстанавливают потраченное право. Если право потрачено, а достоверной записанной квитанции нет, результат — `unknown` и ноль новых вызовов, даже если стенд знает, что передачи не было. Локальный lock, читаемость и ID журнала не доказывают отсутствие прежней попытки. При недоказанной целостности журнала или владении также не передавать. Потеря/откат серверного журнала вне эксперимента.

**Единственная позитивная квитанция в этом эксперименте:** Pi наблюдал конкретное custom-сообщение как инициатора подготавливаемого хода. Публичный `before_agent_start` даёт `messageType=custom`, сверенные `event.message.details` и `ctx.sessionManager.getSessionId()` до начала agent loop. Передать наблюдение асинхронному писателю, не блокируя Pi; сохранить запись локально, затем идемпотентно опубликовать её в fake API. Квитанция не означает, что запрос дошёл до провайдера, ход завершился или задача принята/выполнена. Сразу после commit spend fake API хранит `unknown` при отсутствии квитанции; записанная квитанция подтверждает только эту границу, а spend остаётся израсходованным.

**Независимый oracle:** на каждый `before_agent_start` назначать свежий токен, сохраняя тип инициатора, session ID и details/prompt. В `before_provider_headers` помечать токен только при `ctx.model.provider == "artel-fixture"` и ожидаемом ID модели; fixture конфигурирует единственный числовой loopback endpoint. Fixture отдельно фиксирует фактически полученное полное тело запроса для токена. Тест сверяет первый запрос токена с событием, идентичностью, поколением, сессией, попыткой и уникальным литеральным маркером. Маркер в истории не доказывает новую доставку: отдельный ручной ход со старым маркером получает другой токен, `messageType=user` и ноль bridge-квитанций. Отключить инструменты, ретраи и compaction; считать запросы отдельно по каждому токену. Неподдерживаемый хук, отсутствующий токен или барьер — сценарий не измерен. Callback и fixture trace в логике восстановления не участвуют; без записанной Pi-квитанции результат остаётся `unknown` при любом показании oracle.

## Подход и проверки

Файлы стенда и отчёт — `docs/experiments/pi-bridge-delivery/`, отдельно от первого эксперимента и поставки. Изоляция: чистое окружение, приватные HOME/XDG/Pi agent/session dirs, эфемерные loopback endpoints, вымышленные значения. Фиксация намерения и приёма: файл/переименование и `fsync` на проверенном Linux-стенде, явные ошибки вместо предположения о durability. Проверять только process crash при сохранённых файлах, не power loss. Родительский тестовый процесс управляет только своими дочерними процессами, синхронизирует точки сбоя по явным сигналам, не по таймингам сна; процессовые watchdog и зачистка по всем путям. Раздельные моменты записи состояния и получения ответа. Источник доказательства факта передачи — независимый счётчик/trace fixture-провайдера, а не внутренний статус bridge; эти свидетельства не предоставляются логике восстановления как недоступный в продукте oracle. Если безопасная конфигурация Pi или fixture не подтверждается, остановиться.

Во время плана и между правками — адресные тесты затронутых сценариев; завершение каждой задачи — `make lint test build` и её дополнительные гейты. Полный `make check` и Arch `make package-check` — в конце на итоговом кандидате перед публикацией. Сбой обязательного гейта не обходить; временные данные и полный raw trace не коммитить. Проверка существующих шаблонов/ссылок не выдаёт эксперимент за выполненный.

### Task 2: Exercise the SDK delivery and crash matrix
- [x] Подключить фиктивную инъекцию через `createAgentSession`/inline extension pinned Pi SDK. Адресный runner задаёт обязательные `PI_TEST_PACKAGE`, `PROBE_ROOT` и Node, проверяет версию/ресурсы и пишет полный trace только в приватный временный каталог вне worktree; команда воспроизведения фиксируется в README. Ожидается `node --test docs/experiments/pi-bridge-delivery/*.test.mjs` для модели и отдельная изолированная SDK-команда для crash-матрицы. Сначала положительный контроль: синтетическое сообщение порождает один коррелированный запрос, результат виден в trace; повтор запроса не порождает второго.
- [x] По явным барьерам проверить: потерю ответа до/после commit допуска; падение до серверного расходования права, после серверного расходования до/после ответа, затем до/после commit локальной попытки, но до вызова; падение bridge или Pi после передачи при удержанном fixture-запросе до записи свидетельства; обрыв HTTP-соединения после приёма полного тела, но до response headers; падение после записи свидетельства до POST и потерю ответа до/после commit квитанции; отказ записи попытки (ноль вызовов) и отказ записи свидетельства (unknown). На восстановлении открыть тот же журнал новым процессом, подать повтор через обычный вход и сравнить журнал, fake API и независимые счётчики Pi/провайдера до и после. Записанная квитанция переотправляется с тем же ключом без повторного вызова Pi; незаписанная после попытки не реконструируется из тестового oracle. Для ветки, где внешний координатор погиб, а Pi остался жив, отдельно проверить позднее завершение старого хода и невозможность новой попытки после его рестарта. Не выдавать один общий SDK-process crash за два разных сценария.
- [x] Для уже начатой доставки проверить обычный redelivery при отсутствующем локальном журнале, восстановленной читаемой копии до попытки с тем же ID и конкурирующем втором отправителе. Повтор не увеличивает счётчики Pi/провайдера. Отдельно проверить безопасное продолжение с доказанно нерасходованным правом и сохранным журналом.
- [x] Проверить отзыв поколения до допуска, после допуска до последней проверки, и после передачи. До последней проверки ожидается ноль вызовов; после передачи позднее свидетельство может остаться историческим и не меняет активное поколение. Явно отметить остаточное окно между последней проверкой и вызовом Pi.
- [x] Прогнать матрицу и `make lint test build`.

### Task 3: Exercise real Pi TUI in an isolated PTY
- [x] Повторить положительный сценарий в настоящем Pi CLI в изолированном PTY без окна. Использовать отдельные тестовые `-e` с `--no-extensions --no-skills --no-prompt-templates --no-context-files --no-themes --no-mcp --no-builtin-tools`, приватные ресурсы и существующий шаблон PTY. Точные команды runner/README и типовые assertions сверять с pinned Pi; внешние настройки не читать.
- [x] **Manual first:** начать ручной ход, удержать fixture-запрос, затем предъявить Artel-сообщение при busy. Ровно один user-запрос, ноль spend, ноль вызовов Pi bridge, локальное ожидание Artel без Pi follow-up. В процессе Pi после всех await на spend/журнал идёт финальная проверка `ctx.isIdle()` непосредственно перед синхронным `sendMessage`. ## Результат предварительной проверки плана

На момент проверки плана (до запуска матриц) разрешённый базовый квитанционный факт — наблюдение `before_agent_start` с `messageType=custom`, точными details и session ID. Это не provider ACK и не completion. Fixture trace только проверяет фактический HTTP-запрос внешним oracle; bridge не использует его для разблокировки восстановления. Codex отдельно согласовал manual-first/custom-first ветки PTY без Enter во время streaming в базовом сценарии. Проверенный runner оставляет raw traces вне worktree, а в Git сохраняет лишь сокращённый отчёт без секретов. Публичные типы Pi 1.5.2 подтверждают нужные поля хуков; на этой предварительной проверке сценарии ещё не выполнялись; измеренные результаты приведены в отчёте Task 4.

## Приёмка

Воспроизводимое доказательство поведения на каждой заявленной границе важнее зелёного прототипа. Результаты SDK и PTY отдельно; разница между известным неприёмом, наблюдённым ходом и unknown видна в отчёте. Не запускать следующий этап автоматически; договориться о продуктовом контракте по результатам.
