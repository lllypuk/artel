# Artel 5а — сдача задачи и ревью точного Git-кандидата

## Обзор

Владелец видит в карточке, какой результат сдал агент, к какой версии относится внешний прогон revmux и что осталось проверить. Pi уже запущен в обычном Linux-терминале, поручение идёт через 4a. revmux запускает владелец вне Artel. `artelctl` читает локальные структурированные артефакты, Artel сохраняет краткое доказательство. Stage 4b доступен, но не обязателен в сценарии приёмки.

Критерии: видны репозиторий, полные `base`/`head`, идентификатор прогона, источник сведений о SHA, ссылка на отчёт, полнота проверки и краткий итог. Повторный импорт не дублирует запись; отсутствие или деградация обязательного источника не выглядят как ревью без замечаний; сдача новой версии сохраняет старый отчёт в истории, но не засчитывает его для новой. Владелец решает, принимать ли результат, существующими ручными действиями. Импорт не меняет состояние задачи, очередь или назначение и не разрешает merge/deploy.

Не входят: автоназначение, запуск Pi/revmux из Artel, вердикт или автозакрытие задачи, Git/CI-бот, фоновая проверка HEAD, загрузка отчётов по сети, копирование сырых отчётов, новые платформы, действия на живых сервисах.

## Подход к разработке и проверкам

Сначала тесты для контракта хранения и импортёра; для Qt — минимальный UI с проверками на production QML. Изолировать тесты временными путями, приватным HOME и ephemeral ports. При изменениях запускать `make lint test`, к концу каждой кодовой задачи — `make lint test build`; чинить красные проверки до следующего шага. Полный `make check` и на Arch `make package-check` — один раз на финальном кандидате после содержательного ревью, перед публикацией. План подлежит ревью до реализации. Обновлять этот план при изменении согласованного объёма.

## Решение и детали контракта

- **Владелец фиксирует кандидата отдельно от отчёта.** `artelctl results submit` принимает UUID задачи, локальный репозиторий, полные `base`/`head` и необязательный краткий итог. Идентичность repo для 5а — канонический абсолютный путь Git common-dir (`git rev-parse --path-format=absolute --git-common-dir` с разрешением symlink), одинаковый для linked worktrees; отдельный клон или перенос каталога — другая идентичность. CLI проверяет, что оба полных SHA обозначают коммиты этого репозитория. Текущий означает «последний сданный владельцем», а не локальный HEAD; прежние кандидаты неизменяемы. Смена текущего — CAS по ID ожидаемой сдачи (включая отсутствие). Стабильный `--request-id` повторно используется после неизвестного ответа: сервер проверяет квитанцию до CAS, возвращает исходный ответ без повторной записи и отклоняет другой payload с тем же ключом.
- **Отчёт импортируется отдельно:** `artelctl reviews attach` читает `manifest.json` и `findings.json` указанного каталога, проверяет поддерживаемую форму и отправляет только нормализованные данные. Не исполняет команды из файлов, не открывает URL и не передаёт сырые тексты findings. Локальные артефакты ограничены по размеру; отсутствующий/повреждённый файл — ошибка импорта, а валидный прогон без обязательного источника — сохранённое неполное ревью.
- **Привязка до запуска.** Владелец фиксирует канонический repo, revmux `task/run` и два полных SHA в локальной записи, которую затем передаёт `reviews attach` вместе с ID сдачи и каталогом отчёта. Запускает revmux в чистом worktree со scope, где оба SHA заданы литералами, без `HEAD`/имён веток; хранит один канонический архив прогонов на repo. CLI сверяет `task/run` записи с manifest, а repo и диапазон — с выбранной сдачей, не с текущей. Owner API в транзакции сам загружает сдачу по ID, проверяет её принадлежность задаче и требует точного совпадения переданных repo/base/head с сохранёнными. Для записи и бизнес-ключа он использует значения из сохранённой сдачи, а не из HTTP-запроса. В 5а источник диапазона всегда `operator`: это заявление владельца, не независимая аттестация. Не извлекать SHA из текста отчёта и не поддерживать `artifact` без проверенного формата.
- **Ошибки и полнота.** Ошибка без записи: непригодный JSON/неподдерживаемая форма, незавершённая пара, несовпадающие идентификаторы запуска или метаданные окончания там, где есть в обоих файлах, дубли строк источников или противоречивое описание одной роли в двух файлах. Roster из manifest — ожидание, не факт ответа: для полноты использовать фактически отчитавшиеся источники в `findings.json`. Владелец указывает обязательные пары `name+executor`. Корректный завершённый отчёт сохраняется неполным, если список требований пуст, обязательная пара отсутствует/заменена или деградировала по списку либо флагу. Деградацию только необязательного источника показать отдельно: она не делает неполными обязательные источники. Сохранить список требований и причины неполноты. Ноль находок у отчитавшегося источника не означает отсутствие ответа.
- **Краткий итог.** Показать полноту именно обязательных источников и счётчики по импортированному отчёту, отдельно `pre_existing` и `open_questions`. Не называть замечание проверенным без явного признака в артефакте. Ноль импортированных замечаний не означает отсутствие открытых вопросов, прохождение всех проверок или приёмку.
- **Уникальность.** Бизнес-ключ прогона `(repo, revmux task, run)` не включает задачу Artel и ID сдачи и не зависит от ключа HTTP-повтора. Та же привязка с теми же нормализованными данными возвращает исходную запись; перенос на другую задачу/сдачу или другой payload под тем же ключом дают конфликт без перезаписи. Один и тот же `task/run` допустим в разных репозиториях. Привязка к прежней сдаче остаётся исторической, даже если импорт запоздал. Ссылка отображается как данные; нет автоматического открытия локальных путей/произвольных URI.
- **Ручное решение.** Карточка передаёт ожидаемый ID из того же загруженного представления, которое видит владелец. Сбой или незавершённая загрузка не означают отсутствие сдачи. В транзакции существующего `POST /v1/tasks/{id}/transition` сервер сначала проверяет квитанцию точного повтора, затем до перехода проверяет ожидаемый ID и версию задачи. При наличии сдачи пропущенное поле, явное отсутствие ID или другой ID дают `409` даже при актуальной версии задачи. Пропуск поля совместим со старым клиентом только при фактическом отсутствии сдачи. Конфликт требует перечитать карточку, а не повторять решение автоматически. SSE обновляет результат независимо от редактора. Успешное ревью не становится обязательным условием перехода, импорт статуса не меняет.

Для закрытия продуктового критерия 5а отдельно согласовать демонстрацию с настоящим revmux на одноразовом проекте: Pi в обычном терминале, небольшой коммит, сделанный самим Pi по поручению, внешний revmux для чистого `base..head`, импорт отчёта, новый коммит и решение владельца. Фикстура из задачи 4 не заменяет эту демонстрацию. Затем, с отдельного разрешения, провести пилот на одной задаче реального проекта и выбрать первую операцию для автоматизации в 5б. Не менять рабочую установку, не выполнять merge/deploy.
