# Автономная команда агентов в Mattermost

## Overview

Принято стратегическое решение: **превратить agent-shatrov в базовое «тело» автономного
агента**, из которого поднимается 2–3 инстанса с разными системными промптами
(«должностями»: аналитик, разработчик, тестировщик), подключённых к общему Mattermost.
Координация между агентами — **без центрального оркестратора**: агенты общаются сами
через @-mentions в каналах/DM, как живая команда.

Это **осознанная смена парадигмы**:

| | Оркестрируемая модель | **Автономная модель (выбрана)** |
|---|---|---|
| Координация | центральный state-machine гоняет ботов по фазам | агенты сами решают, кого и когда позвать |
| Состояние воркфлоу | в SQLite, переходы через host-tools | живёт в разговоре/треде |
| Гарантия фаз | строгая (аналитика→разработка→тестирование) | нет, зависит от самих агентов |
| Гибкость | низкая | **высокая (приоритет)** |
| Сложность | оркестратор + хост-тулы + state-machine | предохранители от петель в каждом инстансе |

**Что решает:** постановка задач ИИ-команде (продуктовая аналитика, разработка,
тестирование) через единый интерфейс Mattermost, с максимальной гибкостью и
минимальной инфраструктурой координации.

## Context

В `~/Project` лежат три релевантных проекта — важно зафиксировать их роли, чтобы не
путаться в пересечении концептов:

- **agent-shatrov** — личный Telegram-ассистент. Сильная база: богатые инструменты
  (wiki, notes, web, shell, code_runner, browser, news), `pi_coder` (само-доработка),
  multi-provider LLM с fallback, memory, диалоги, токены. Транспорт изолирован в
  `internal/telegram/`. **→ выбран как «тело» агента.**
- **devbots** — команда ботов в Mattermost на ядре `pi --mode rpc` + центральный
  оркестратор (workflow-фазы, host-tools, SQLite state-machine, делегирование,
  loop-detection). **→ становится донором**, не фронтом дальнейшей разработки:
  оркестратор решает задачу (гарантия фаз), сознательно deprioritизированную.
- **flowra** — отдельный веб-продукт (чат + канбан-доска для людей, Mongo/Keycloak/HTMX).
  **→ к этой задаче отношения не имеет**, доска нужна только ботам под капотом.

### Почему agent-shatrov, а не devbots

devbots ценен **инфраструктурой координации**, а не «ботами» как таковыми. Выбрав
автономную модель, мы отказываемся именно от этой инфраструктуры — вкладывать новые
усилия в достройку devbots-оркестратора смысла больше нет. Зато у agent-shatrov уже
есть то, чего devbots не имеет: **полнофункциональные агенты** с реальными
инструментами и самообновлением (`pi_coder`). Допиливать transport-абстракцию и
защиту от петель в agent-shatrov — в сумме меньше работы, чем достраивать devbots
до «богатых агентов».

### Что переиспользуем из devbots (donor, копируем логику — не тащим зависимость)

| Из devbots | Зачем |
|---|---|
| `internal/mm/` (REST + WebSocket клиент Mattermost) | образец для `MattermostTransport` |
| Loop detection (10 warn / 15 suppress на тред, reset на human message) | паттерн для предохранителя №2 |
| DM-детекция по `channel_type`, @-mention-маршрутизация | логика для расширенного auth |

## Solution Overview

### 1. Абстракция транспорта

Вынести `internal/telegram/` за интерфейс, не ломая существующий Telegram:

```go
// internal/transport/transport.go (новый пакет)
type Transport interface {
    Send(ctx context.Context, m Message) error
    Messages() <-chan InboundMessage   // события входящих сообщений
    Close() error
}
```

`internal/telegram/bot.go` становится одной из реализаций. `cmd/agent/main.go` выбирает
реализацию по `config.transport: "telegram" | "mattermost"`. Ядро агента (`internal/agent`)
перестаёт знать про конкретный транспорт — знает только интерфейс.

Сегодня `internal/telegram/` ссылается только из `config` и `main` — рефакторинг чистый,
переписывания ядра не требуется.

### 2. MattermostTransport

Новая реализация интерфейса на основе Mattermost REST + WebSocket (паттерн — из devbots
`internal/mm/`). Один инстанс агента = один токен бота Mattermost + один WebSocket.

### 3. Расширение auth: реакция на других ботов

Сейчас auth — по людям (`telegram.allowed_users` = chat_id). Для команды агентов нужно
реагировать на @-mention **от других ботов команды**, не только от человека-владельца.
Whitelist имён ботов команды в конфиге; человек-владелец остаётся супервизором.

### 4. Обязательные предохранители (даже при выборе гибкости)

«Гибкость» ≠ «хаос». Три предохранителя обязательны в каждом инстансе, иначе первый
бот-в-бот тред уходит в бесконечность и сжигает токены:

1. **Игнорировать собственные сообщения** (bot_id == sender → skip). Иначе бот отвечает
   сам себе.
2. **Жёсткий лимит итераций на тред** (по образцу devbots: ~10 сообщений ботов → warn,
   ~15 → suppress; reset на сообщение человека). После лимита — стоп и эскалация
   человеку в тред.
3. **Rate-limit ответов** (не чаще N в минуту на тред).

Это ровно та логика, что devbots уже реализовал — берём оттуда, не изобретаем.

### 5. Конфигурация инстансов

Подъём «2–3 инстансов» = 2–3 конфига + 2–3 токена Mattermost. Каждый конфиг задаёт:
`transport`, токен, **системный промпт = «должность»**, whitelist соседних ботов,
параметры предохранителей. Один и тот же бинарник, разные роли.

## Development Approach

- **Testing approach**: Regular (код → тесты). Каждая задача включает тесты.
- Завершать задачу полностью перед переходом к следующей.
- Запускать `make lint test` после каждого изменения.
- Transport-абстракция (Task 1) — **первая и обязательная**: без неё остальные задачи
  не имеют куда встать.
- devbots трогаем **только на чтение** (как референс), код в agent-shatrov не копипастим
  вслепую — переписываем под свои интерфейсы.

## Testing Strategy

- **Unit tests** для каждой реализации `Transport` (Telegram остаётся покрыт; MM — через
  httptest + mock WebSocket).
- **Safeguards tests** — табличные сценарии: self-message skip, лимит итераций,
  rate-limit, reset на human message.
- **Auth tests** — реакция на @-mention от бота-соседа vs от человека vs от чужого.
- Интеграционный тест «двух агентов в одном треде» — опционально, через in-process
  хаб (без живого Mattermost).
