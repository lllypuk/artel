## Объём и приёмка

Владелец явно включает доставку для одной уже привязанной тестируемой Pi-сессии, из выбранной задачи отправляет текстовое поручение и видит историю именно этой задачи. `arteld` сохраняет текст и выбранное назначение до попытки передачи; перезапуск daemon, Qt или Pi не стирает историю. Повтор отправки **того же HTTP-запроса** с тем же ключом не создаёт новое поручение. Автоматического повтора уже израсходованной попытки нет, даже если стенд знает, что вызова Pi не было. Ручной ввод Pi не подменяется и не ставится bridge в steer/follow-up.

Только направление владелец → Pi. Не входят: вопросы и ответы, захват диалогов/вывода инструментов, рассылка, запуск агентов, автоматическая смена состояния задачи или выбор другого получателя, внешний доступ, установка на рабочую машину. Перед отправкой явно показать назначение и предупредить, что текст может уйти настроенному в Pi провайдеру как часть контекста. Статусы не подтверждают получение запроса провайдером, завершение хода или задачи.

## Контекст и выбранное решение

- `internal/store/store.go` управляет миграциями SQLite; текущие данные имеют схемы v1/v2. Owner HTTP и идемпотентность — `internal/api/`, `api/openapi.yaml`.
- В `cmd/arteld/main.go` уже есть отдельный локальный observer HTTP listener на Unix-сокете. `internal/observerapi/http.go` отделяет телеметрию и owner-операции; существующий observer-токен не имеет права читать поручения.
- `integrations/pi-observer/` — явно загружаемое расширение; `desktop/src/apiclient.cpp`, `panel.cpp` и `ManualWorkspace.qml` — точки интеграции владельца. C++ ведёт сеть и черновик, QML отображает данные и действия. Токены не передаются в QML.
- **Согласован вариант 1:** тот же Unix-сокет, отдельные маршруты и отдельный delivery-токен. Тот же observer-токен с расширенными правами отклонён: это неявно даёт доступ существующим установкам. Второй сокет не нужен: разделяем права и маршруты без ещё одного listener. На owner TCP нет bridge-маршрутов, на Unix-сокете нет owner-маршрутов.

## Технический контракт

**Включение и назначение.** По умолчанию выключено; один слот на инсталляцию, занятый допуском `pending` либо `active`. CLI генерирует секрет и атомарно сохраняет одну приватную pending-запись с installation ID, неизменяемыми ID допуска/журнала, полным исходным запросом, секретом и ключом повтора **до первого HTTP-запроса**. На сервер передаётся только verifier. `enable --resume` сверяет ID БД и повторяет исходный запрос без регенерации; исторический ответ `enable` не подтверждает текущую активность. Ожидаемый installation ID проверяет сам сервер до обработки `enable`, включая replay. Перед локальной публикацией CLI через owner `GET /v1/observers/{observer_id}/delivery/{delivery_binding_id}` сверяет текущий статус и точную идентичность исходного допуска; исторический ответ не разрешает запись. Артефакты хранятся по отдельному пути для каждого неизменяемого ID допуска; нет общего файла «текущий допуск», который может заменить старый `resume`. CLI завершает bootstrap только исходной pending-записи: подтверждённый bootstrap читает без записи, существующий журнал проверяет, не перезаписывает. Journal создаётся один раз при подтверждённом первом bootstrap, с эксклюзивным созданием; если нельзя отличить незавершённое создание от утраты журнала, остановиться и требовать новый явный допуск. Подтверждённый конфиг публикуется атомарно после проверки журнала. Отзыв между owner GET и записью не активирует устаревший допуск: observer сообщает только текущее назначение, `attach` повторно его проверяет. `pending` можно отозвать. Токены не попадают в argv, результаты, URL, логи или промпты.

Допуск связывает installation, observer, runtime, project, binding generation, точный Pi session ID и исходный journal ID, проверяемый независимо от файла. При `enable` CAS использует `observer.version`; в доставке проверяется полное назначение и `generation`, а не версия от несвязанного `prune`. Обновлённое расширение на обычном опросе observer context получает только метаданные допуска и подхватывает подтверждённый конфиг по заранее определённому приватному пути рядом с локальным observer config, без перезапуска уже привязанного runtime. Путь не приходит с сервера. Без явного допуска и подтверждённого файла writer не стартует. После открытия исходного журнала и подтверждённого `attach` допуск становится `active`. CAS-маркер writer (ID процесса) долговечен в SQLite; доступность — отдельное подтверждение текущего writer в памяти daemon (TTL 10 с, обновление каждые 2 с), сбрасывается при рестарте daemon и смене CAS-маркера. Обновление readiness — `POST /delivery/v1/ready` после успешного `attach` или сверки потерянного ACK; `GET context` ничего не меняет. Новый owner POST разрешён только для `active` со свежей готовностью; `pending` или неготовый writer — отказ без записи, совпавшие owner replay не зависят от готовности. Остановка runtime или появление `candidate` не освобождает слот; при остановке без перепривязки владелец освобождает его явным revoke. Отзыв, отвязка или фактическое изменение назначения атомарно инвалидируют допуск и освобождают слот. Новая Pi-сессия не наследует допуск или очередь.

**Owner API.** `POST /v1/tasks/{task_id}/messages` с `Idempotency-Key` и телом `text`, `delivery_binding_id` (неизменяемый ID допуска), `instance_id` (ожидаемый ID БД); `GET /v1/tasks/{task_id}/messages?after=<cursor>` — история в порядке записи с непрозрачным курсором, до 50 записей на страницу. `GET /v1/tasks/{task_id}/delivery` возвращает точное назначение, состояние допуска и доступность writer без токена или текста. `GET /v1/tasks/{task_id}/messages?ids=<id,...>` перечитывает до 50 видимых строк независимо от курсора. `PUT /v1/observers/{observer_id}/delivery` принимает ожидаемый `observer.version`, точное назначение, ID допуска и исходного журнала и verifier; `POST /v1/observers/{observer_id}/delivery/revoke` принимает ID допуска. Для всех owner-мутаций обязателен `Idempotency-Key`. Сначала owner-аутентификация; для POST поручения сверить `instance_id` с БД в той же транзакции до поиска replay или новой записи. Затем проверить совпавший replay: вернуть исходное поручение даже после отзыва или закрытия задачи, несовместимое тело — конфликт. Проверки актуального назначения относятся к новой записи, не к совпавшему replay. Этот контракт не применяется к bridge `spend`. Новое поручение — непустой UTF‑8, не более 8 КиБ, без NUL, с сохранением принятых переносов/байтов текста; тело запроса ограничено до декодирования. Для новой записи в той же транзакции проверить `task.project_id == binding.project_id`: отправка только в проект допуска, если проект не архивирован и задача не в терминальном состоянии. Не применять эти проверки актуальности к совпавшему replay в той же БД. При закрытии задачи или архивировании проекта в той же транзакции сохранить необратимую отметку блокировки для всех существующих поручений задачи/проекта: нерасходованные больше не выдаются, для потраченных отметка запрещает будущий `verify`, но не стирает попытку или квитанцию. История и причина сохраняются. Повторное открытие или разархивирование не разблокирует старые поручения. История поручений отделена от доменных переходов и базового snapshot/SSE; UI обновляет её отдельным bounded polling только для выбранной задачи. Не публиковать текст в телеметрии, общих событиях, логах или диагностике.

**Доставка.** На общем Unix listener: `GET /delivery/v1/context`, `GET /delivery/v1/next`, `POST /delivery/v1/attach`, `/delivery/v1/ready`, `/delivery/v1/spend`, `/delivery/v1/verify`, `/delivery/v1/receipt`. Без long polling и отдельного `claim`: резервирование не даёт полезной гарантии поверх `spend`. Общий транспортный фильтр (Host/Origin, лимиты и формат), затем точный список маршрутов и собственная аутентификация каждого канала. `context` не возвращает текст; `next` читает его только после проверки текущего writer и активного точного назначения. Для JSON-ответа `next` — отдельный лимит 64 КиБ на обеих сторонах: до 48 КиБ для 8 КиБ текста при шестибайтовом экранировании каждого байта плюс ограниченные метаданные. Не использовать для `next` observer-лимит 16 КиБ; oversized-ответ отклоняется до разбора. Граничный текст с управляющими символами (кроме NUL) проходит round-trip без изменений.

Writer сначала приобретает эксклюзивную блокировку на стабильном объекте **на весь срок работы**, независимо от атомарной замены файла журнала; затем проверяет исходный журнал и вызывает `attach` с новым случайным ID процесса и CAS по предыдущему владельцу. Начало polling/отправки только после подтверждения CAS; при потерянном ACK, в том числе после рестарта daemon, `GET context` сверяет долговечный CAS-маркер с тем же новым ID процесса и неизменным назначением под той же блокировкой. Совпадение подтверждает владение, не право вызова и не readiness; прежний маркер допускает повтор исходного CAS, иной или неясный — остановку. Перед снятием блокировки остановить polling, отозвать локальные права и завершить либо обезвредить старые callbacks. PID, имя файла и совпавший journal ID по отдельности не доказывают владение; проверку выбранного механизма блокировки выполнить в первой задаче. Нет доказательства владения или целостности — остановка. Не обещаем обнаружить произвольный откат к валидной копии с тем же ID: отсутствие локальной записи не отменяет серверный spend.

`next` выбирает старейшее доступное поручение точного назначения без выдачи права. Bridge проверяет idle, сохраняет intent и запрашивает `spend`. Транзакция сверяет владельца, journal ID, сообщение, назначение, поколение и Pi-сессию, расходует одно право и сохраняет `attempt_id` с `unknown` до ответа. Право может содержаться только в ответе той операции `spend`, которая впервые закоммитила расход. Ни один replay или запрос состояния не возвращает право (не использовать replay сохранённого HTTP body для `spend`); `verify` только подтверждает уже полученное право того же writer. До расходования восстановление допустимо лишь при доказанном unspent на сервере и проверенном исходном журнале; после расходования — никогда не вызывать Pi заново. После него — запись попытки и финальный `verify`, затем один синхронный участок: сверить текущее локальное владение, проверить `ctx.isIdle()`, погасить право в памяти и вызвать `sendMessage(..., {triggerTurn:true})` без `await`. Право существует только в памяти и привязано к `attempt_id` и текущему writer. Второй callback и повтор `verify` не восстанавливают погашенное право. Busy, отказ или неопределённый `verify`, утрата владения и shutdown уничтожают локальное право без вызова; синхронная ошибка Pi не восстанавливает его. При новой busy после spend — без вызова, результат `unknown`; при busy до spend — ждать вне очереди Pi. Отзыв после проверки назначения и до вызова остаётся измеренным окном, не гарантией отмены. Если журнал отсутствует, повреждён, заменён или запись попытки не подтверждена — не вызывать Pi. Потеря/откат данных сервера и power loss не считаются доказанным восстановлением.

**Квитанция и UI.** Только `before_agent_start` с `messageType=custom`, точными details (ID сообщения и попытки) и ID Pi-сессии передаётся асинхронному писателю. Записать квитанцию локально, затем публиковать идемпотентно с тем же ключом. О событии сообщает bridge; daemon сверяет форму, идентичность, попытку и назначение. Новый writer с тем же действующим назначением и исходным журналом может переопубликовать сохранённую квитанцию прежней попытки с исходным ключом, но не приобретает её право вызова. Новая регистрация Pi с другим runtime не может восстановить такую публикацию за старый допуск. Потеря ACK при действующем допуске восстанавливается повтором публикации, не вызовом Pi. `stored` → «Сохранено»; `unknown` → «Исход неизвестен»; `observed` → «Pi начал подготовку хода». Для сохранённого поручения с недействительным назначением показать причину, скрывать историю нельзя. UX не предлагает автоматическую повторную передачу и не меняет статус задачи. Черновик при ошибках остаётся в Qt; при потере ответа POST повторять исходные instance/task/binding/body/key, не подменяя их при смене задачи. При замене БД повтор не запускать. Polling выбранной задачи перечитывает состояния видимых сообщений, отдельно от подгрузки страниц истории. Входящие вопросы и произвольный ответ Pi не отображаются.

| Событие | `next` / `spend` / `verify` | `receipt` и история |
|---|---|---|
| Отзыв допуска/observer, отвязка, другое поколение или runtime | Старое назначение больше не выдаёт текст, не расходует право и не подтверждает вызов. После успешного `verify` уже выдаваемый вызов может состояться. | Впервые пришедшую квитанцию отклонить, сохранить `unknown`. Уже закоммиченный `observed` не понижать даже при потере ACK и отказе старому токену на replay; владелец видит его в истории. |

История доступна. |

## Подход и тесты

TDD для миграции, прав, идемпотентности, автомата и восстановления; QML и команды — реализация с проверками на существующих фикстурах. Идти по порядку, не переходить к следующей задаче с красным гейтом. После правок запускать адресные проверки и обязательный проектный `make lint test`; в конце задачи — указанный дополнительный гейт. Полный `make check` и Arch `make package-check` — на итоговом кандидате один раз, повтор после значимых исправлений. Автотесты работают в приватных временных каталогах с фиктивным loopback-провайдером, временным сокетом и pinned Pi. Никаких рабочих токенов, системных настроек и автоматической установки зависимостей. Таймаут или отсутствующий барьер — провал измерения, не PASS.
