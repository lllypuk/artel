# Artel v2: opt-in наблюдение за Pi и переход в agterm

## Overview

Статус: план подготовлен; один review сабагентом выполнен, замечания учтены. Владелец выбрал bounded retirement markers и явное переподключение при исчерпании квоты (см. Review outcome). Владелец отдельным поручением разрешил закоммитить план в новую feature-ветку и запустить ralphex. Разрешена реализация только в границах этого плана; merge/push/deploy этим поручением не разрешены.

Следующий срез после ручной desktop-панели: существующий, явно подключённый Pi сообщает собственную идентичность, активность и доступность; владелец связывает наблюдение с проектом и видит его в Artel. Из desktop можно по явному клику открыть заявленную сессию agterm, если локальный адаптер проверил адрес.

Это **наблюдение, не управление агентами**. Не добавлять отправку prompt/message/steer/follow-up, инструменты агента, задания, автоматический запуск Pi, назначение writer, исполнение очереди, вопросы/согласования, MR/CI orchestration, импорт старых досок, remote access, mini/Caddy, Android или реализацию macOS. Не менять семантику `owner_manual` существующих задач. Дочерние процессы Pi допустимы только как изолированные тестовые fixtures с детерминированным локальным провайдером.

Пользователь поручил подготовить этот план, провести один review в сабагенте, затем явно разрешил его запуск через ralphex. Исполнитель работает в новой feature-ветке от принятого main; не устанавливает системные пакеты, не активирует службы, не меняет глобальную конфигурацию Pi/agterm/Omarchy, не выполняет merge/main push/deploy.

## Development Approach

- TDD для границ регистрации, поколений, auth и recovery; каждый task включает новые/изменённые тесты и их запуск. Не отмечать checkbox за описание будущего теста.
- Один task полностью, включая его gates, до следующего. Не ослаблять прежние тесты/таймауты/валидацию ради зелёного результата. После изменения кода обязательно `make lint test`; общий обязательный минимум перед завершением **каждого** task — `make lint test build`, плюс перечисленные в task дополнительные gates (как требует docs/development.md).
- Сначала подтвердить наблюдаемые публичные hooks в изолированном Pi, затем фиксировать server/client contract. Неподтверждённый обязательный hook — blocker, а не terminal scraping или патч Pi.
- Обновлять план при изменении объёма; несовместимый контракт, недоступная dependency или необходимость новых полномочий останавливают выполнение. Не превращать техническую неизвестность в молчаливое расширение задачи.
- Не импортировать credentials, историю или расширения текущего разработчика в tests. Все processes, HOME/XDG/PI_CODING_AGENT_DIR, sockets, session files и provider fixtures — отдельные временные; cleanup убирает только их.
- Опциональный runtime для владельца не означает опциональные tests: новая интеграция обязательно проверяется в `make check`/CI. Отсутствие test dependency — явный preflight failure, не skip. `arteld`, `artelctl`, desktop продолжают запускаться без Pi/Node.

## Technical Contract

### Раздельные поверхности и provisioning

1. Текущий owner API остаётся на loopback с прежним owner token. Owner-only endpoints: `PUT /v1/observers/{observer_id}` (создать), `GET /v1/observers` (projection), `PATCH /v1/observers/{observer_id}/binding` (выбрать runtime + project или отвязать), `POST /v1/observers/{observer_id}/revoke`, `POST /v1/observers/{observer_id}/prune`.
2. При отсутствии нового флага observer listener **не создаётся**. Opt-in `arteld --observer-socket PATH`: HTTP over Unix socket, отдельный router/middleware. Путь задаёт локальный владелец, например `$XDG_RUNTIME_DIR/artel/observer.sock`; не приходит из agent request. Приватная директория 0700, socket 0600; no-follow/owner/type checks, лимит длины пути, отдельный lifetime lock сокета. Нельзя удалить чужой/активный socket или обычный файл. Stale socket после SIGKILL можно убрать только под lock, после проверки inode/type/owner и отсутствия слушателя; race/сомнение — отказ. Graceful shutdown удаляет только собственный socket.
3. Observer surface: `GET /observer/v1/context?runtime_id=UUID`, `POST /observer/v1/register`, `PUT /observer/v1/report`. Контекст возвращает только своё назначение/generation и database identity; не задачи, owner secrets или других наблюдателей. Host фиксирован `artel-observer`, Origin/absolute URL запрещены, JSON ≤16 KiB, строгие DTO, body/read/write deadlines. Owner token не принимается на этой поверхности; observer credential не принимается ни одним owner endpoint, включая snapshot/events/SSE.
4. Credential — отдельный 32-byte random bearer для одного `observer_id`; сервер хранит только SHA-256 verifier с уникальным индексом. Сравнение/lookup не логирует secret; ID и область выводятся из credential. Revocation немедленно запрещает register/context/report. Credentials не включать в projection/audit/QML/error body.
5. `artelctl observer provision --name NAME --observer-socket PATH --output CONFIG` создаёт UUID, token file и private config локально, безопасно и без перезаписи; до HTTP отправки fsync/atomic write. Owner PUT получает только verifier и label, UUID Idempotency-Key; receipt содержит только публичный результат. Config хранит observer UUID, ожидаемый database UUID, socket path, token-file path, provisioning idempotency key и полный канонический PUT payload (включая исходный label и verifier). До PUT его status=`pending`: extension отказывается использовать такой config. Потеря ответа не требует нового credential: `artelctl observer provision --resume CONFIG` после перезапуска CLI повторяет сохранённые payload/key, без пересборки label из новых аргументов; verifier сверяется с локальным token file. Только после подтверждённого успешного ответа с ожидаемыми ID/database UUID CLI атомарно и с fsync меняет status на `confirmed`, разрешая extension подключение. Сбой до этой записи оставляет `pending` и допускает безопасный resume; API collision/content mismatch не затирается. Secret никогда не печатается, в argv не передаётся, в receipt не попадает. `list/bind/unbind/revoke` работают через owner API; все операции имеют понятные JSON/exit-code результаты.
6. Этот token ограничивает API, но не является sandbox против произвольного кода того же Unix UID, читающего файлы владельца. Это ограничение явно показать в документации.

### Identity, registration и generation

- Различать persistent `database_instance_id` (существующий `instance_id`), stable `observer_id` (credential), `pi_session_id` (история Pi), fresh random `runtime_id` (инкарнация extension) и server-controlled `generation`. Не называть runtime ID просто `instance_id`.
- Provision создаёт unbound observer. `register` аутентифицирован, содержит runtime/session IDs, reason, Pi/bridge version, cwd, provider/model identifiers, optional terminal hint. Не назначает проект/роль автоматически по cwd/PID/модели/унаследованному окружению.
- Новый `session_start`, включая reload/new/resume/fork, всегда новый runtime ID и **candidate**, требующий явного owner bind. Это сознательная консервативная граница пилота. Reconnect/рестарт API при том же живом runtime не создаёт новую инкарнацию и не требует rebind. Один observer может иметь несколько кандидатов, но лишь один выбранный runtime.
- Register идемпотентен по `(observer_id,runtime_id)` и immutable registration identity; повтор сохранённой runtime не создаёт runtime/generation, иное тело для того же runtime — 409. После prune остаётся retirement marker: register/context/report этого runtime возвращают 409 `runtime_retired`, не восстанавливают кандидата и не выделяют новую generation. Это явное terminal-состояние вместо воспроизведения удалённого registration response. Mutable activity/model передаются report, не меняют registration identity.
- Owner binding использует observer `expected_version` и UUID Idempotency-Key. Атомарно назначает ровно одного runtime этому observer, project FK проверяется до записи; archived/unknown project запрещён. Переключение runtime или проекта/отвязка увеличивает generation, старые reports её не проходят. Заменённый runtime становится superseded и не возвращается автоматически через register. Для повторного выбора нужен новый runtime и owner bind. Разные observers могут наблюдать один проект: это **не** multiple-writer authorization.
- Context/register response содержит disposition (`candidate/bound/superseded/revoked`), generation, own binding и database UUID. Контекст superseded runtime не выдаёт ему новое активное назначение. Bridge после generation-conflict один раз сверяет собственный context; не угадывает +1 и не повторяет old report как новый bind.
- Config pin database UUID проверяется до register/report. При замене БД/неожиданном UUID — остановить передачу и показать диагностическое состояние; не перепривязываться автоматически. Миграция и обычный restart сохраняют database UUID. Утерянный credential/401 тоже не запускает provisioning из extension.

### Activity, freshness и bounded state

- Report — только latest-state: runtime, generation, строго растущий `report_seq`, `activity = unknown/idle/working/waiting_user`, tool count, optional provider/model, lifecycle `running/stopped`. Идентичный повтор того же seq/body отвечает duplicate **без продления freshness**; тот же seq с иным body или меньший seq — 409. Namespace seq — `(runtime_id,generation)`, после подтверждённой смены generation новый счётчик; сервер хранит последний seq/hash в одной строке, не receipt на каждый heartbeat.
- Idle определяется `agent_settled`/reconciliation через `ctx.isIdle()`, не `agent_end`. Tool callbacks ведут set ID активных tools, не один boolean. Состояние ожидания UI-подтверждения — факт Pi, не вопрос/разрешение Artel. Бизнес-готовность задачи не выводится из этих сигналов.
- Heartbeat раз в 5 s, status changes coalesce минимум 250 ms, ≤4 reports/s/runtime; network deadline 2 s, capped exponential reconnect 1–30 s с jitter. Одна in-flight отправка + один latest pending state; нет истории tool outputs или бесконечной очереди. `session_shutdown` прекращает timers, abort старых requests и делает ограниченную best-effort stop delivery, не задерживая Pi более 250 ms. Если stop потерян — stale, не обещание crash detection без задержки.
- Server freshness отдельно от activity: fresh до 20 s после **нового принятого** report, иначе stale; graceful stopped отдельно. Использовать monotonic elapsed time процесса, server wall-clock только для отображения last_seen. После рестарта daemon все сохранённые runtime неизвестны/stale до нового report, даже если last_seen выглядит свежим. Старый delayed/replayed packet не меняет current binding и не оживляет старый runtime. Потеря heartbeat не освобождает writer и не меняет task state.
- Отдельные observer tables/store methods с короткими транзакциями: principal/verifier, runtime/latest metadata + seq/hash, binding/version. Не пропускать heartbeat через domain `Store.Apply`, domain receipts или `owner_manual` events. Owner registration/bind/revoke audit — отдельная таблица; observer telemetry не маскируется под owner action.
- Лимиты пилота: 256 observers (включая revoked); максимум 8 полных runtime records/observer; максимум 1024 уникальных зарегистрированных runtime IDs за жизнь credential, включая pruned; 256 bounded owner-audit entries/observer с oldest-first pruning только этого журнала. Использовать latest-state вместо event history. Квоты проверяются атомарно в registration transaction; новый runtime при исчерпании любой квоты получает 409 `capacity_exceeded` с причиной. Повтор существующей непрореженной runtime не расходует квоту и продолжает работать при лимите.
- Owner-only `artelctl observer prune --id UUID` под binding/version CAS удаляет payload/телеметрию только unbound/superseded/stopped runtimes, **никогда текущей bound runtime, даже stopped, и никогда manual project history**. В той же транзакции сохраняется компактный permanent retirement marker `(observer_id,runtime_id)` без cwd/model/session/terminal metadata; concurrent register/report не может оживить удаляемую runtime. И полный record, и marker занимают одну identity из квоты 1024; prune освобождает только квоту полных records (8), не identity quota. Markers не имеют TTL и не вытесняются oldest-first вместе с audit; их запрет действует после restart daemon и повторных prune. Marker не включается в обычную UI projection; доступны счётчики квот.
- При исчерпании 1024 identities сохраняются heartbeat/report/reconnect текущей bound runtime, но новые runtime не регистрируются. Владелец явно provision нового observer/credential, подключает extension к нему, подтверждает новую project binding и revoke старого; автоматической замены/копирования binding нет. Старый observer/verifier/markers остаются revoked, не удаляются ради повторного использования токена. Если исчерпана и общая квота 256 observers — явный capacity blocker, без неописанного auto-GC или снятия лимитов. Secret/key/label, строки/UUID/enum, cwd≤4096, metadata≤16 KiB и списки имеют явную валидацию. Переполнение не убирает активную привязку.
- Observer GET projection ограничена лимитами registry, с `database_instance_id`, server time, records/versions/freshness. Доступна только owner. Desktop poll каждые 2 s, только пока видим соответствующий экран, один request in-flight; timeout/backoff/generation cancellation. При недоступном API явно offline/unknown, не вечное fresh по старой карточке. Это отдельный канал: существующие snapshot/event_seq/SSE/history остаются без observer events.

### Pi extension и desktop

- Новый каталог `integrations/pi-observer/`: TypeScript, manifest/lockfile, build/typecheck/unit/SDK/TUI tests. Начальный supported Pi — ровно 1.5.2, Node ≥22.23.2; dependency на Pi 1.5.2 pinned для tests, остальные dev dependencies фиксировать lockfile. Проверка `VERSION`/required hooks до подключения; неподдержанная версия — явный disabled, без fallback на private API. До реализации читать актуальные локальные Pi docs/extensions.md, examples/extensions и cross-references полностью.
- Extension загружается только явным Pi `-e PATH` из документированного package artifact, config path через `ARTEL_OBSERVER_CONFIG`. Нет auto-discovery установки в `.pi/`, глобальных settings, собственного provider/model выбора или launch Pi из Artel. Без config — inert. С config, но неверными правами/версией — диагностический отказ без secret. Resource startup только в session_start, cleanup идемпотентный; factory не открывает сеть.
- Собираются только whitelisted metadata. Не отправлять prompt/response, tool name/args/output, titles/text UI prompts, full env, session files, history, provider credentials. При auth/API сбое Pi продолжает собственную работу; extension показывает краткую status-индикацию без prompt injection и не блокирует event handlers сетью.
- Owner UI: общий список кандидатов и выбранный project's observer list, явные bind/rebind/unbind/revoke/prune с CAS и подтверждением опасных для наблюдения действий. Display role/label — имя наблюдателя, не назначение обязанностей. Provision secret только CLI, UI содержит инструкцию без secret textbox. Показать runtime/session IDs, версию, model, last_seen, activity/freshness, candidate/superseded, и предупреждение «Активность Pi не означает завершение задачи».
- Отдельные C++ `ObserverClient`/model и QML `ObserverPanel`; не переиспользовать manual mutation slot/draft. Связать с выбранным проектом без возможности поменять его под грязным редактором. Старые async replies и смена database не обновляют другую карточку; выбранные runtime/project IDs повторно сверяются перед owner mutation. RU/EN и доступность по клавиатуре как у foundation.

### Navigation adapter

- `desktop/src/agtermadapter.{h,cpp}` с injectable process runner; аргументы фиксированного CLI whitelist, без shell. Socket path только из owner-local desktop option `--agterm-socket PATH` (либо его собственного AGTERM_SOCKET), не из observer metadata. Terminal hint содержит полные window/session/pane UUID, без произвольного socket/command.
- Hint может быть унаследован дочерним Pi и **не доказывает**, что процесс находится в панели. UI подписывает переход «Открыть заявленную сессию agterm», показывает происхождение/непроверенность. Нет автоматического bind по terminal hint. Отсутствие/agterm inconsistency не мешает direct Pi→Artel observation.
- По click: read-only version/capability probe, `window list --json`, затем `tree --window FULL_WINDOW_UUID --json` для открытых окон: дерево window-scoped, запрос без window не является поиском по приложению. Не доверять hinted/frontmost window после move. Максимум 16 окон, общий output ≤1 MiB и deadline 2 s на одну попытку обнаружения; превышение — unavailable, не частичный успешный поиск. Точное совпадение полного session+pane UUID, актуальный window из соответствующего tree; однозначность обязательна. Затем `session select` с полными target/window/socket. При исчезнувшем/неоднозначном/неразвёрнутом target — показать отказ, не создавать/realize новую сессию с потенциальным restore command. Ошибка или malformed output никогда не приводит к выбору `active`, имени, cwd или prefix.
- Baseline не выполняет pane focus, restore/restart/new/type/mail/overlay. При swap открывается сессия с явной пометкой, что точный pane focus не гарантирован; при move повторить tree максимум один раз, иначе отказ. Таймаут 2 s, output cap 1 MiB, QObject/QProcess lifecycle cleanup. Никакого systemd/Hyprland remote execution для активации.
- Тестовый fake agtermctl обязателен; настоящий Omarchy/Wayland foreground smoke — отдельное действие владельца после реализации, не checkbox автономного исполнителя.

## Testing Strategy

- Go: incremental migration и preservation v1 identities/data/events/receipts; Unix socket path/permission/lock safety; owner vs observer token isolation; revoked/foreign runtime; CAS bind/revoke/report races; duplicate/out-of-order; lost responses; bounds/rate/clock/restart.
- TypeScript: typecheck/lint/unit + реальные публичные SDK hooks и минимум один автоматизированный TUI PTY lifecycle smoke на pinned Pi и локальном deterministic provider. ## Post-Completion

Выполнение плана разрешено отдельным поручением владельца. Локальная установка пакета/включение observer listener и подключение первой своей Pi-сессии по-прежнему требуют отдельного разрешения. Реальный Omarchy/agterm foreground smoke и наблюдение пользовательской сессии выполняются отдельным согласованным действием; remote CI требует публикации кандидата и проверки exact HEAD. Merge/main push/deploy не входят в план.

Следующий возможный этап — долговечные сообщения и вопросы. До него нужен отдельный delivery/recovery эксперимент с dispatch intent, receipt journal, input race и conservative unknown outcomes. Успех read-only наблюдения не закрывает этот гейт и не даёт разрешение отправлять поручения или запускать команду.
