# Artel v2: эксперимент Pi bridge №1

Дата: 2026-11-17.
Статус: выполнена ограниченная SDK-проверка по прямому разрешению владельца.
Продуктовый bridge не реализован; полный технический гейт не закрыт.
Основание: [контракт Pi bridge](20261117-artel-v2-pi-bridge.md).

## Окружение и воспроизведение

- Pi **1.5.2**, Node **22.23.2**, Linux.
- Реальный `createAgentSession` / `DefaultResourceLoader`, inline extension и `bindExtensions({ mode: 'json' })`; не mock методов Pi, но и не CLI/TUI.
- Отдельные HOME/XDG/agent/session directories; очищенное окружение через `env -i`, без ключей провайдеров и AGTERM-переменных.
- Один явный inline extension, отсутствие обнаруженных context files, пустой набор инструментов проверяются assertions.
- Настоящий локальный HTTP/SSE fixture на `127.0.0.1` со случайным портом; постоянный ответ `FIXTURE_OK`, управляемая задержка ответа. Внешних LLM-запросов нет.
- ModelRuntime: отдельные auth/model paths, `allowModelNetwork: false`, `refreshOnCreate: false`. Продуктовые конфиги и глобальные расширения не изменены.
- SIGKILL только собственным тестовым дочерним процессам. Это тест process crash, не отключение питания.

## Результаты: 10 сценариев подтвердились

PASS здесь означает подтверждение ожидаемого поведения, включая опасные границы, а не десять гарантий надёжности.

| № | Сценарий | Наблюдение |
|---|---|---|
| 1 | `appendEntry` до начала разговора | Entry доступна в памяти; session-файла нет |
| 2 | Idle `sendMessage(custom, { triggerTurn: true })` | Return `undefined`; один запрос модели; custom ID/details видны в `before_agent_start`, `message_end` и затем в JSONL; `input` не вызывается |
| 3 | `sendUserMessage` с `input → handled` | Return `undefined`; модель не вызывается, пользовательское сообщение не появляется в истории |
| 4 | `sendUserMessage` в занятую сессию без deliverAs | Return `undefined`, затем error callback `send_user_message`; отвергнутое сообщение не сохраняется |
| 5 | Сообщение удерживается вызывающей стороной до `agent_settled` | Пока Pi занят, внутренней pending-очереди нет; из settled-handler запускается ровно один следующий custom-ход |
| 6 | Повтор custom с одинаковым `message_id` | Две записи и два хода: Pi не дедуплицирует по нашему ID |
| 7 | Обычное повторное открытие истории | Session ID и custom details сохраняются |
| 8 | SIGKILL после appendEntry, до разговора | Session-файла по-прежнему нет |
| 9 | SIGKILL после получения первого custom-запроса fixture-провайдером, до ответа | Запрос уже получен, session-файла нет; отсутствие истории не доказывает, что передачи не было |
| 10 | SIGKILL при queued follow-up в уже сохранённом разговоре | Предыдущий разговор восстановим, queued пользовательского сообщения нет ни в JSONL, ни при открытии SessionManager |

В сценарии 5 очередь — **in-memory переменная тестового вызывающего кода**, не реализация долговечной очереди Artel. Проверено поведение Pi на границе settled, не серверная транзакция или доставка через HTTP Artel.

## Что важно для контракта

### Custom message — подходящий кандидат, но не новая роль провайдера

Внутри Pi происхождение и `details.message_id` доступны в событиях и истории. В OpenAI-compatible payload custom превращается в **user-role сообщение**. `details` туда не передаются: fixture проверяет отсутствие специального metadata sentinel и наличие читаемого ID из content.

Следствие: в content нужен явный конверт «сообщение агента / автор / тип / задача / ID», а в details — структурная корреляция для bridge. Нельзя рассчитывать, что модель прочитает details, или утверждать, что custom автоматически отделён от user на уровне API провайдера. Такой конверт помогает атрибуции, но не является механизмом авторизации и не защищает от prompt injection сам по себе.

### Наблюдаемая квитанция не равна durable ACK

В trace первого custom-хода `message_end` custom и даже обработчик `message_end` assistant наблюдаются при `fileExists: false`; к `agent_end`/`agent_settled` файл уже есть. Это наблюдение данной версии и последовательности обработчиков, не обещание такого порядка всех будущих версий.

Сам `message_end` нельзя объявлять durable receipt. Обычное успешное переоткрытие доказывает сохранение в данном прогоне, но не fsync/power-loss гарантию. До завершения первого custom-ответа даже состоявшийся запрос провайдеру может не оставить session-файла.

### Unknown остаётся необходимым состоянием

Серверный intent, события Pi и отдельный receipt journal нужны совместно. Наличие receipt показывает только указанную границу; отсутствие истории после crash не разрешает слепой resend. Идемпотентность должна обеспечиваться Artel/bridge: одинаковый ID в details сам по себе ничего не блокирует.

## Что пока НЕ проверено

- Интерактивное отображение custom в настоящем TUI; соседство с ручным вводом и точная гонка idle→busy.
- Reload, new/resume/fork через настоящий runtime lifecycle, compaction, отзыв старых контекстов. Обычное SDK-переоткрытие файла не заменяет эти сценарии.
- Аутентификация/регистрация Artel, поколения назначений, scoped credentials и permissions.
- Fake Artel API, потеря HTTP-ответов intent/receipt, outbox/dedup, disk-full и crash-safe локальный journal.
- Автоматические ретраи, provider failures и reconnect.
- Реальные LLM, принятие задачи, исполнение инструментов, содержательное согласование Продактом.
- macOS, восстановление agterm/zmx и отключение питания.

## Следующий ограниченный эксперимент

1. Зафиксировать минимальный fake Artel API и receipt journal в изолированном стенде: generation, ID, intent, correlation evidence, unknown.
2. Проверить потерю ответа intent, повтор запроса, отозванное назначение и restart bridge: ни одного автоматического повторного хода при unknown.
3. Выполнить TUI smoke отдельно, с тем же fixture-провайдером; сравнить события/историю с SDK и проверить ручной ввод в гонке.
4. Только после этих проверок фиксировать окончательный способ доставки и исполняемый план первого продуктового среза.
