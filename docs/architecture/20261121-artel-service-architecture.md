# Artel: верхнеуровневая архитектура сервиса

Дата: 2026-11-21.
Статус: целевое направление, согласованное в обсуждении с владельцем. Это не описание уже реализованных возможностей, не исполняемый план и не разрешение запускать следующий этап. Порядок этапов — в [дорожной карте](../roadmap.md).

Документ уточняет [исходное направление Artel v2](20261117-artel-v2-direction.md). Исторические документы и доказательства сохраняются; там, где здесь зафиксировано более позднее решение владельца, приоритет имеет этот документ.

## 1. Пользователь и назначение

Artel — **личная рабочая панель одного разработчика, фактически CTO**, который развивает несколько проектов и поддерживает сервисы со своей командой Pi-агентов.

Главный сценарий — **автоматизированная работа Pi-агентов над эпиками, задачами и багами**, которые владелец ставит и уточняет в том числе в диалоге с CTO-подобным агентом. Владелец задаёт цели и границы; CTO-агент помогает с декомпозицией и планом, Developer выполняет работу, Product и другие роли подключаются к своим решениям. Наблюдение за терминалами подчинено этому циклу, а не является продуктом само по себе.

Для владельца остаются центральными вопросы: «Что происходит с моими проектами, что выполняется и где сейчас нужно моё решение?».

Artel:

- хранит проекты, работы, очереди, обсуждения, решения и доказательства;
- подключает и при отсутствии сессии запускает разрешённых Pi-участников;
- доставляет явные сообщения между владельцем и участниками, а также Developer ↔ Product;
- управляет циклом проверки Git-кандидата, включая последующий автоматический запуск revmux;
- открывает план для ревью и diff точного кандидата MR/PR в `revdiff` в системном браузере;
- оставляет владельцу приоритеты, разрешения, приёмку и операции с внешними системами.

Это не мультипользовательский SaaS, не универсальный workflow engine и не замена Git, CI, MR или Pi. Codex CLI и Claude Code не являются целевыми харнесами; роли не привязаны к конкретной модели или провайдеру.

## 2. Реализованное и целевое

Уже реализованы Go daemon/CLI, SQLite, нативный Qt desktop, ручные проекты/задачи/очереди/история, opt-in observer Pi, доставка поручений владельца, вопросы владельцу и ручной импорт результата с ревью Git-кандидата.

Текущее приложение открывает **Team**. Целевой первый экран — **глобальная Board**. Текущий delivery допускает один активный owner-granted binding и не является готовым agent-to-agent протоколом. Текущая интеграция не запускает Pi или revmux автоматически и не имеет встроенного открытия плана/кандидата в revdiff.

Поэтому Board, типы работ, Review/revmux, консультации Developer ↔ Product и управляемый запуск Pi являются отдельными будущими этапами. Архитектурное согласование не означает, что они уже работают.

## 3. Контекст системы

```text
Владелец — один разработчик / CTO
        |
        v
Qt desktop -------------------- artelctl
        |                            |
        +-------- owner HTTP API ----+
                                     |
                                     v
                              arteld (Go) ---------------- SQLite
               проекты / работы / участники / история       (только arteld)
               сообщения / доставка / запуски / результаты
                                     |
             +-----------------------+----------------------+
             |                       |                      |
      локальный agent API      Pi supervisor          адаптеры проверок
             |                       |                      |
      Pi extension             жизненный цикл Pi       Git / revmux / revdiff
             |                       |                      |
       существующая или              Pi TUI/SDK/RPC       отчёты и кандидаты
       управляемая Pi-сессия
```

`agterm` находится вне этого обязательного контура. Он может использоваться desktop как необязательный адаптер навигации к существующему терминалу. Его mailbox не является целевым транспортом Artel и не должен зеркалировать управляемые сообщения.

## 4. Границы компонентов

### arteld

Единственный владелец SQLite и доменных транзакций. Отвечает за идентичность, авторизацию, проекты, работы, очереди, участников, назначения, сообщения, outbox, операции запуска, результаты и историю. Мутации и создание соответствующей outbox-записи сохраняются атомарно.

### Desktop и CLI

Используют owner HTTP API и никогда не обращаются к SQLite напрямую. В desktop логика и асинхронная сеть остаются в C++; QML отвечает за представление и действия. QML не получает credentials и не запускает shell, Pi, revmux или revdiff.

CLI обслуживает локальные операции владельца, диагностику и изолированные интеграции через тот же контракт. Наличие CLI-команды не означает разрешения выполнять её против рабочего окружения без согласования.

### Pi supervisor

Отдельная серверная возможность жизненного цикла: создать разрешённый процесс, найти его по сохранённой операции, восстановить сохранённую Pi-сессию и согласовать runtime с extension. Supervisor не определяет продуктовые решения и не выдаёт полномочия по cwd, PID, модели или имени панели.

Технический интерфейс запуска через поддерживаемый Pi SDK/RPC выбирается отдельным экспериментом и планом. Supervisor не является неявным разрешением на автоматический запуск произвольных команд.

### Pi extension

Объявляет точные `pi_session_id` и `runtime_id`, возможности и доступность; получает только разрешённые сообщения через локальный agent API; предоставляет явные инструменты консультации, вопроса и отчёта. Observer остаётся независимой телеметрией и не переносит диалоги или tool payloads.

### Git, revmux и revdiff

Git идентифицирует кандидата полными `base`/`head`. revmux предоставляет внешний отчёт и сведения о полноте источников. Artel связывает их с задачей, но не объявляет неполный отчёт успешным и не приравнивает отчёт к приёмке.

`revdiff` — целевой адаптер содержательного просмотра: владелец открывает версию плана для ревью и diff точного `base..head`, на котором будет создаваться MR/PR, в системном браузере. Открытие revdiff не меняет кандидат, не запускает revmux, не принимает результат и не выполняет merge/deploy.

## 5. Модель работ

### Project

Постоянная область разработки или поддержки: сервис, приложение либо согласованный набор компонентов. Проект сохраняет собственную очередь и ограничение одной исполняемой работы `in_progress`. Подключение Product или reviewer к той же работе не занимает дополнительное место очереди.

### Epic, Task и Bug

| Тип | Правило |
|---|---|
| **Epic** | Группирует дочерние работы своего проекта. Не является исполняемым поручением, не входит в очередь и не занимает `in_progress`. Имеет вычисляемую сводку и отдельное явное закрытие. |
| **Task** | Обычная исполняемая работа с постановкой, критериями, очередью, результатом и историей. |
| **Bug** | Исполняемая работа над дефектом с ожидаемым/фактическим поведением и доказательством исправления. Не получает автоматически более высокий приоритет. |

Task и Bug могут иметь необязательную связь с Epic. Тип не заменяет статус или приоритет. При будущей миграции существующие записи получают тип Task.

CTO-подобный Pi-агент помогает владельцу обсуждать цель, формировать Epic/Task/Bug и декомпозировать разрешённый объём. Его предложение становится постановкой только через сохранённое действие владельца; роль не получает owner credential, право приёмки или неограниченное разрешение на реализацию.

Первый Board использует существующие состояния `backlog`, `queued`, `in_progress`, `done`, `cancelled`. **Review не добавляется как визуальная колонка заранее**: он требует отдельной серверной модели переходов, ответственности и повторной проверки.

## 6. Целевой рабочий интерфейс

### Глобальная Board

По умолчанию Board показывает Task и Bug всех активных проектов. Плитка содержит проект, тип, название и Epic при наличии. Цветная полоса помогает различать проекты, но текст остаётся обязательным носителем смысла.

Основные элементы:

- Projects и фильтры Project/Epic;
- блок и фильтр **«Ждёт тебя»** для открытых вопросов владельцу;
- колонки действующих серверных состояний; done/cancelled можно сворачивать;
- точные индикаторы: «Кандидат сдан» относится к текущему `result_id`, а «Отчёт приложен» означает отчёт, прикреплённый именно к этому `result_id`; в карточке видны repo и полный `base..head`;
- сворачиваемая сводка подключённых Pi и свежести наблюдения без shell/dialogue payloads.

Фильтр изменяет только видимость и не перестраивает полную очередь. Внутри `queued` сохраняется последовательность каждого проекта. Действия карточки и возможный drag вызывают одни и те же серверные команды; UI не обходит зависимости, свободное место `in_progress`, неизвестный исход или приёмку.

Остановка Pi не двигает плитку. Сдача кандидата и получение отчёта не закрывают работу автоматически.

### Карточка работы

Карточка объединяет постановку, Epic, текущий статус, участников и сессии, консультации, вопросы владельцу, решения, Git-кандидаты, запуски revmux, отчёты и историю. Из неё открываются ревью версии плана и revdiff точного кандидата MR/PR. Возврат из карточки сохраняет контекст Board и фильтры.

Team и Connections остаются доступны как вторичные экраны диагностики и подключения. Целевой Board — отдельный redesign; `PRODUCT.md`, `DESIGN.md` и startup-тесты обновляются вместе с его реализацией, а не заранее.

## 7. Явные сообщения и история задачи

Artel — основной долговечный транспорт управляемых сообщений. Для Developer ↔ Product достаточно одного task-scoped маршрута консультации:

1. Отправитель явно адресует вопрос участнику задачи.
2. Сервер выводит автора из credential, проверяет маршрут и текущие допуски.
3. Текст и outbox сохраняются одной транзакцией.
4. Extension получателя передаёт отдельный `artel-agent-message`, только когда Pi свободен.
5. Получатель явно отвечает со ссылкой на исходную консультацию; receipt не создаёт ответ автоматически.

В историю работы попадают все явно отправленные консультации и ответы с автором, адресатом, связью вопроса и состоянием доставки. Полный локальный диалог Pi, произвольный ввод и вызовы инструментов не копируются. Предложение Product, формальное согласование версии и решение владельца — разные записи.

Для первого среза Product не получает owner credential и не обращается к владельцу напрямую. Developer эскалирует вопрос через существующий допуск 4b; ответ владельца сохраняется в карточке и может быть явно передан Product.

Доставка повторно использует проверенные принципы `next → spend → verify → receipt`, но требует нового протокола участников: текущий единственный owner binding нельзя просто выдать двум Pi. Состояния `stored` / `unknown` / `observed` не повышаются до «прочитано моделью», «согласовано» или «выполнено». Неизвестный исход не вызывает автоматический повтор.

## 8. Жизненный цикл Pi

Artel управляет сессией только в пределах явно разрешённой работы и роли. Открытие карточки, observer config или получение консультации сами по себе не создают новый процесс.

Для одного назначения задачи/участника первоначальный запуск и resume используют **общую атомарную резервацию**, а не независимые operation ID. Повтор той же операции и конкурирующие запросы к одному назначению получают существующую резервацию. Даже два одновременных resume с разными operation ID создают не более одного runtime. Если для роли уже существует внешняя Pi без записи операции в Artel, требуется явная точная привязка. При неоднозначности Artel останавливается на сверке и не создаёт процесс.

| Ситуация | Поведение |
|---|---|
| Живая точная привязка | Обязательно переиспользовать подтверждённые session/runtime. Занятая Pi получает обычное сообщение после освобождения. |
| Первого запуска ещё не было | Первое явное поручение владельца разрешает запуск этой роли. До побочного действия атомарно резервируется назначение и сохраняется operation ID; supervisor находит процесс по операции после сбоя или перезапуска arteld. |
| Остановка подтверждена | Владелец выбирает «Возобновить». Та же резервация назначения защищает resume; Artel открывает сохранённую Pi-сессию в новом runtime и заново подтверждает допуск. Замена истории — отдельный явный выбор. |
| Состояние или исход запуска неизвестны | Сверить операцию supervisor и живую Pi. Heartbeat и пустой observer не доказывают остановку. До установления исхода второй процесс не запускается. |

Старые delivery attempts с неизвестным исходом не переносятся на замену. Новый runtime не наследует допуск только потому, что повторил Pi session UUID. Два одновременных resume одного остановленного назначения используют одну резервацию и не создают два процесса. Первый технический эксперимент lifecycle должен проверить потерю ответа сразу после запуска без agterm.

## 9. Последующий Review с revmux

После Board на действующих статусах Review проектируется как отдельный доменный цикл:

1. Назначенный разработчик после выполнения реализации использует узкий scoped допуск на сдачу **текущего `result_id`** в Review; owner credential и общее право ручных переходов ему не передаются.
2. Artel проверяет кандидата, атомарно резервирует операцию и автоматически запускает один revmux в чистом диапазоне.
3. Отчёт и полнота обязательных источников привязываются к этому кандидату.
4. Разработчик исправляет замечания в несколько итераций. Каждая явная пересдача нового result ID автоматически резервирует один прогон нового кандидата; повтор той же операции возвращает существующий прогон. Новый `head` требует нового кандидата и прогона; прежние отчёты остаются историей, а поздний отчёт относится к прежнему кандидату.
5. Повтор той же сдачи не создаёт второй revmux. Неполный, деградировавший или неизвестный прогон не считается отсутствием замечаний.
6. Владелец может открыть план и diff точного кандидата MR/PR в revdiff, затем отдельно принять или вернуть работу. Завершение revmux не принимает работу, не закрывает её автоматически и не разрешает merge/deploy.

Для этапа Review достаточно внешнего revmux и уже доступного ручного пути доработки. Автоматическая доставка замечаний в запущенную Pi-сессию не является его обязательной частью и не создаёт зависимость от последующих agent-to-agent консультаций.

До плана Review отдельно определяются состояние работы во время исправлений, влияние Review на единственное `in_progress`, ответственные за повторный запуск и возврат на доработку, если место `in_progress` уже занято другой работой. Автоматический запуск revmux в этом будущем этапе не меняет границу уже влитого 5а, где владелец запускает revmux и прикрепляет отчёт вручную.

## 10. Надёжность, доступ и дальнейшие роли

- Все мутации имеют идемпотентность и проверки ожидаемой версии/поколения. Повтор с другим payload — конфликт.
- Перед внешним побочным действием сохраняется восстановимая операция. Потерянный ответ означает unknown, а не свободное разрешение повторить запуск.
- Отдельные local scoped credentials различают observer, owner delivery и будущих участников. Отзыв закрывает новые операции, но не обещает отменить уже выполняющийся процесс.
- Текст явного сообщения становится контекстом выбранного Pi provider; сервер не исполняет его как команду и не выдаёт дополнительных разрешений модели.
- Событие Pi, heartbeat, окончание хода, receipt, отчёт revmux, решение Product и приёмка владельца остаются разными фактами.
- Lead, reviewer и другие роли рассматриваются следующими этапами. Будущая статусная модель может требовать решение определённой роли по конкретной версии, без универсального редактора графов и обязательного Product-гейта для каждой правки.

Внешний доступ, macOS, mini/Caddy и мобильные сценарии остаются самостоятельными последующими решениями и не нужны локальной Board, консультациям или Review.
