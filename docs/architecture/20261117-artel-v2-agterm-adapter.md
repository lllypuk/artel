# Artel v2: адаптер agterm-linux

Дата: 2026-11-17.
Статус: уточнение архитектуры по форку владельца, не реализация и не разрешение менять живые сессии.
Связанные документы: [направление](20261117-artel-v2-direction.md), [Pi bridge](20261117-artel-v2-pi-bridge.md).

## 1. Базовая реализация и границы проверки

Владелец использует [melonamin/agterm-linux](https://github.com/melonamin/agterm-linux), а не только upstream macOS agterm. Исследована ветка `linux-port`, commit `7f95d856d10df58d1d3964e1416d668aae721708`.

README описывает GTK4/libadwaita frontend на Swift поверх общего `agtermCore` и общего CLI `agtermctl`. Совместимость с upstream — цель проекта, не гарантия идентичного поведения всех платформ и версий.

Read-only запрос к работающему приложению показал **0.40.0**, commit `85ceed8c77dd532905b96f71d2752c5139a5a380`; установленная версия совпадает с работающей. Это **другая ревизия**, чем исследованный HEAD форка. Локальная справка подтверждает команды select/focus, но проверка справки не является тестом GUI. Перезапуски, переключения окон, отправка сообщений и изменения конфигурации не выполнялись.

## 2. Роль адаптера

Artel использует agterm только для:

- обнаружения доступных терминальных адресов;
- отображения доступности перехода в терминал;
- перехода по явному действию владельца;
- наблюдения структурных изменений, чтобы обновить адреса.

Pi extension общается с Artel напрямую. Задачи, ответы владельца, квитанции и права не доставляются через terminal input, mailbox или overlay. Адаптер не читает legacy mailbox и не дублирует туда сообщения Artel.

В первой версии достаточно оболочки над `agtermctl --json` с ограниченным набором команд, timeout, лимитом ответа и передачей аргументов без shell interpolation. Прямой Unix-socket клиент возможен позже; он не нужен для обхода отсутствующей функции CLI. Не экспортировать произвольную команду agterm через Artel API.

## 3. Адреса и доверие

Предлагаемый `terminal_ref` содержит:

- ID локального подключения Artel к экземпляру agterm;
- полный session UUID и стабильный `paneID`;
- последние наблюдавшиеся window/workspace UUID;
- время проверки и состояние `available / stale / unavailable / unsupported`.

Путь socket хранится в локальной конфигурации подключения, а не принимается как произвольный путь из удалённого запроса. `AGTERM_SOCKET` необходимо явно передавать CLI. Не использовать `active`, короткий префикс UUID или имя сессии для адресации агента.

Начальные AGTERM-переменные — подсказка для привязки, не доказательство личности Pi. После перемещения сессии или swap/promotion роль панели и workspace из окружения могут устареть. Текущее расположение определяется по tree и стабильному `paneID`. Наследование переменных дочерним процессом не передаёт полномочий родителя.

`terminal_ref` не заменяет `agent_id`, `pi_session_id`, `instance_id` или `binding_generation`. При смене процесса agterm навигационная привязка перепроверяется; это не повод автоматически менять Pi generation либо освобождать writer.

## 4. «Открыть агента»

Предлагаемая последовательность:

1. Проверить локальную доступность нужного подключения и прочитать актуальное дерево нужных окон.
2. Найти полный session UUID и `paneID`; подтвердить текущую связь с экземпляром Pi. При неоднозначности не выбирать панель по похожему имени/cwd.
3. По явному клику владельца выбрать окно и сессию через `window select` / `session select`.
4. Если возможно, сфокусировать нужную панель и проверить результат; иначе явно сообщить, что открыта только сессия.

**Ограничение:** `session focus` в исследованном исходнике и установленной CLI-справке принимает `primary/split`, физическую позицию или `other`, но не `--pane-id`. Поэтому перевод стабильного токена в роль по свежему tree — best effort с гонкой при одновременном swap. Это не атомарный переход к идентичности панели. `other`/toggle использовать нельзя. При изменении раскладки — повторная сверка либо переход только к сессии с предупреждением; не обещать точный фокус без проверки. Такой fallback допустим для навигации, но никогда не используется для доставки поручений.

Выбор окна внутри agterm не доказывает, что Wayland compositor поднял его над другими приложениями. Реальный переход проверить на Omarchy; платформенную активацию держать вне общего API-контракта.

## 5. События и восстановление наблюдения

В исследованном `ControlEvents.swift`:

- ring хранит по умолчанию 4096 событий в памяти одного процесса;
- курсор — пара `run` и `after`, ответ содержит `next`;
- чтение без курсора возвращает текущий anchor без истории;
- смена процесса, просроченный или опережающий курсор дают явную ошибку;
- `next` учитывает также отфильтрованные события: нельзя заменять его seq последнего показанного события.

Artel использует эти события как сигнал обновить проекцию терминалов, не как журнал выполнения задач. Предлагаемая синхронизация: получить anchor → прочитать snapshot дерева → прочитать события после anchor и перечитать затронутую структуру. Это не атомарный snapshot; при новом разрыве повторить синхронизацию с ограничением попыток и показать stale. Дополнительная периодическая сверка восстанавливает наблюдение после пропусков. Интервалы и лимиты выбрать экспериментом.

После ошибки курсора или рестарта нельзя продолжать старую последовательность как непрерывную. Потерянную историю не восстанавливать из текущего tree. Статус терминала не считается завершением задачи либо ACK сообщения Pi.

## 6. Перезапуск agterm — не один сценарий

Документация различает:

| Режим | Что означает для Artel |
|---|---|
| Fresh shells | Восстановленная раскладка не доказывает наличие прежнего Pi |
| Re-run commands | Повторный запуск команды не равен продолжению прежнего процесса; нужна сверка регистрации Pi |
| Live sessions / zmx | Возможен reattach к живому процессу, но это нужно подтвердить bridge; после потери daemon возможен новый запуск |

Наличие `backedByZmx` — характеристика терминала, не гарантия живости Pi, долговечности его очереди или выполненной задачи. Scratch/overlay не считать постоянным местом writer. Artel не переключает restore mode и не перезапускает агентов автоматически ради восстановления связи.

## 7. Linux/macOS и удалённый клиент

Общий адаптер использует семантику CLI/JSON, а не GTK, SwiftUI или геометрию окон. Особенности активации окна и доступности команд — платформенные capabilities. Версию и commit сохранять для диагностики; возможность не считать доступной только по номеру версии. Неизвестные необязательные поля JSON игнорировать, отсутствие необходимых — явный unsupported.

Будущий macOS-клиент, подключённый к Linux API, не должен пытаться открыть Linux Unix socket локально. Ссылка «открыть терминал» имеет смысл только на машине с соответствующим подключением agterm. На телефоне/другом компьютере — показать отсутствие локального перехода, не выполнять скрытый remote shell. Удалённая презентация agterm не заменяет защищённый API Artel через mini/Caddy.

## 8. Проверки перед реализацией

Только в отдельно разрешённом изолированном стенде, не на действующих разработчиках:

- несколько окон/одноимённых сессий, move, swap, promotion и закрытая панель;
- гонка между tree и focus; корректный fallback к сессии;
- недоступный socket, несовместимая версия, timeout и некорректный JSON;
- переполнение ring и смена run, события во время snapshot;
- независимые рестарты Artel, Pi и agterm; каждый restore mode на отдельных тестовых данных;
- сохранение writer при потере наблюдения, отсутствие повторного задания;
- фактический фокус на Omarchy; в будущем отдельный прогон на macOS;
- Pi bridge продолжает работать без agterm mailbox и при недоступной навигации.
