# Artel v2: контракт интеграции Pi

Дата: 2026-11-17.
Статус: режим ожидания обычных сообщений в Artel до свободной точки Pi согласован владельцем; остальные технические детали требуют эксперимента. НЕ реализованный протокол и НЕ план для `planning:exec`.
Основания: [направление](20261117-artel-v2-direction.md), [сценарий и экраны](20261117-artel-v2-user-flow.md).
Продуктовая реализация не начата. По разрешению владельца выполнен [первый изолированный SDK-эксперимент](20261117-artel-v2-pi-experiment-01.md): 10 проверок, без реальных LLM и инструментов. Действующие сессии, глобальные расширения и конфигурация не менялись.

## 1. Разделение ответственности

- **Artel API:** реестр участников, задачи, очередь, полномочия, долговечные сообщения, разрешения и журнал.
- **Расширение Pi:** идентификация текущего экземпляра сессии, получение допущенных сообщений, передача в харнес, события и инструменты отчётности.
- **Pi:** контекст, модель, выполнение инструментов, собственная история и пользовательский TUI.
- **agterm:** отображение терминала и переход в нужную панель; не основной канал доставки. Целевая Linux-реализация — форк владельца `melonamin/agterm-linux`; [отдельный контракт адаптера](20261117-artel-v2-agterm-adapter.md) учитывает стабильные pane ID, ограничения focus и восстановление терминалов.

Нельзя построить одно общее «сообщение получено = задача выполнена». Протокол отдельно описывает транспорт, передачу в харнес и работу над задачей.

## 2. Что подтверждено чтением установленного Pi

Исследован пакет `@earendil-works/pi-coding-agent` версии **1.5.2** по его локальным package.json, документации и dist-коду. Это статический анализ данной установки, не тест поведения всех версий.

| Наблюдение | Следствие |
|---|---|
| `session_start`/`session_shutdown` различают startup/reload/new/resume/fork; смена runtime не тождественна смерти OS-процесса | Нельзя использовать один PID как идентификатор получателя |
| `agent_end` может предшествовать повтору или продолжению; `agent_settled` означает завершение автоматической активности | Нужен `agent_settled` для сигнала idle, но это не завершение задачи |
| Расширение вызывает `pi.sendUserMessage`, runtime запускает async-вызов и обрабатывает ошибку через `emitError`, не возвращая вызывающему promise этого выполнения | Возврат из метода не является ACK приёма или успеха |
| `input`-обработчик может преобразовать/поглотить ввод; `sendUserMessage` создаёт сообщение роли user | Нельзя считать вход обработанным моделью и нельзя терять происхождение агентных сообщений |
| `sendMessage` поддерживает custom message с details и запуском хода | Кандидат на доставку сообщений Artel с явными автором, ID и типом; выбрать после эксперимента |
| Follow-up ставится во внутреннюю очередь; сам `_queueFollowUp` не пишет её в session manager | Этот путь нельзя считать долговечной очередью Artel без дополнительных доказательств |
| `_persist` не создаёт файл новой сессии, пока нет user/assistant message; custom entries до этого остаются в памяти | `appendEntry` не годится как единственная долговечная квитанция регистрации/приёма |
| В просмотренном `_persist` используются sync write/append без явного fsync | Нельзя приравнивать запись в историю Pi к гарантии сохранения при потере питания |
| История Pi ветвится; custom entries могут наследоваться при fork | Нельзя выдавать новой ветке полномочия старой по скопированному маркеру |

Протокол использует публичные API расширений. Прочитанные внутренние методы — объяснение рисков, а не поддерживаемый интерфейс для будущего кода.

## 3. Идентичность и регистрация

Разделить:

- `project_id`: постоянная область разработки;
- `agent_id`: логический участник, например разработчик проекта;
- `pi_session_id`: идентификатор истории Pi;
- `instance_id`: текущий экземпляр runtime расширения; меняется при reload/replacement;
- `binding_generation`: серверная версия назначения участника экземпляру;
- `run_id`: конкретный запуск/этап, включая дочерние процессы;
- `terminal_ref`: необязательные адреса agterm для навигации.

Расширение объявляет текущую сессию, режим, версии Pi/bridge, cwd, provider/model/reasoning и возможности наблюдения/доставки. Не передаёт ключи провайдеров, всё окружение или полную историю.

Первичное подключение создаёт **неподтверждённого кандидата**, без права получать рабочие поручения. Владелец локально назначает ему роль/проект. Для доверенной прежней привязки возобновление возможно после аутентификации и сверки поколения; неизвестный fork/new или конфликт двух экземпляров не наследует её автоматически.

Сервер допускает одного получателя управляемой работы для данного назначения. Старое поколение не может изменять актуальную задачу или получать новые поручения. Его запоздавшие события при необходимости сохраняются как исторические с явным источником, не перезаписывая текущее состояние.

Истечение heartbeat означает потерю наблюдения, а не освобождение ответственности: старый процесс мог продолжить писать код. Переназначение writer требует сверки/передачи. Это защищает маршруты Artel, но не останавливает произвольный shell уже запущенного Pi.

Дочерний Pi регистрируется как run с ограниченной областью. AGTERM-переменные, скопированные от родителя, не дают права принять его сообщения. Постоянная роль не определяется автоматически по модели, PID, cwd или позиции панели.

## 4. Каналы и минимальные операции

Предлагается один версионированный семантический протокол, доступный расширению и `artelctl`. Конкретные HTTP-path и DTO фиксируются после эксперимента, до реализации серверного контракта.

Локальная интеграция подключается к отдельной поверхности API (например, Unix socket с проверкой прав и scoped credential), не к публикуемому через mini клиентскому endpoint. Публичные методы desktop/mobile не позволяют зарегистрировать агента, выдать роль или прочитать его полномочия. UID и token различают доверенные локальные участники, но не являются sandbox от процесса с полным доступом того же пользователя.

Минимальные группы операций:

| Группа | Назначение |
|---|---|
| Register / resume / heartbeat | Кандидат, привязка, доступность и capabilities |
| Read events / snapshot | События с курсором, восстановление состояния |
| Fetch inbox | Получение доступных сообщений без их удаления |
| Prepare dispatch / record receipt | Проверка версии/поколения и сохранение границы передачи |
| Report task / run | Явный этап, блокер, результат, ссылки на доказательства |
| Send message / ask owner | Консультация либо долговечный вопрос |

Автор и область доступа выводятся сервером из credential, не доверяются произвольным полям тела. Запросы мутаций несут ключ идемпотентности и ожидаемую версию; повтор с тем же ключом и иным содержимым — конфликт, не новая операция.

События имеют server sequence; время клиента служит диагностикой, не единственным порядком. При разрыве retention — явная пересинхронизация snapshot+cursor, без притворного восстановления потерянной истории. Версии API/bridge согласуются; несовместимый клиент может отображать понятную ошибку, но не молча продолжать управляющие операции.

## 5. Доставка: согласованный режим и предлагаемый протокол

### Не держать основную очередь в Pi

Пока Pi занят, обычное поручение/продолжение остаётся в Artel. Bridge забирает его для передачи только в подходящей точке — обычно после `agent_settled`. Состояние idle само по себе не разрешает новую задачу: сервер отдельно проверяет очередь, полномочия и зависимости.

Изменение этого baseline — например, steer для срочной корректировки — отдельная возможность, а не неявное свойство каждого сообщения. Heartbeat и управляющие ACK не запускают LLM. Информационное уведомление может отображаться без нового хода.

Это упрощает восстановление, избегает зависимости от долговечности follow-up и не вмешивается в активный ход. Прямая работа владельца в TUI остаётся возможной; гонка между idle-проверкой и новым ручным вводом должна быть проверена экспериментом и не считается устранённой одной проверкой `isIdle()`.

### Последовательность передачи

1. Сервер атомарно сохраняет сообщение и outbox, привязывает к задаче/версии/адресату.
2. Bridge получает сообщение, но получение не удаляет его и не начинает исполнение.
3. Перед инъекцией сервер проверяет полномочия, generation, ревизию и состояние очереди и сохраняет **dispatch intent**. Повтор того же запроса не выдаёт второй независимый допуск к инъекции.
4. Bridge пытается передать сообщение один раз для этого допуска, с correlation ID и неизменяемым происхождением.
5. События Pi/истории и bridge дают наблюдаемые квитанции: попадание в контекст, начало связанного хода, явное принятие работы. Их точная доступность определяется экспериментом.
6. Итог работы передаётся отдельной операцией, проверяется и сопоставляется с кандидатом. Конец хода не подменяет результат.

Критическая граница между записью intent и инъекцией не атомарна. Если ответ на шаг 3 потерян или процесс упал до/после шага 4, возможен **dispatch unknown**. Сервер и bridge сверяют квитанции и историю только этой зарегистрированной сессии. Отсутствие записи не всегда доказывает отсутствие исполнения. При недостатке доказательств нужен явный разбор, а не автоматический повтор.

Поэтому baseline обещает долговечное поручение и отсутствие слепого повторного запуска, но **не exactly-once выполнение действий агента**. Цена осторожности — иногда требуется восстановительное решение. Усиление автоматического восстановления допускается только после доказательства соответствующей границы в Pi.

### Квитанции и хранение

Artel хранит основной журнал в SQLite с транзакционными гарантиями и явно выбранной политикой durability. Pi custom entries — дополнительные correlation-маркеры, не единственный receipt store и не источник разрешений.

Предлагается небольшой отдельный private journal bridge для критических локальных квитанций/отчётов, не копия всей БД. Способ crash-safe записи, fsync, ограничение размера и compaction журнала проверяются экспериментом. Не начинать новую передачу при отказе необходимой записи.

Техническую телеметрию можно агрегировать и ограничивать по объёму; её потеря отмечается как пробел. Ответы владельца, запросы разрешений и терминальные результаты не должны молча вытесняться из буфера. При исчерпании места — явная ошибка и остановка новых зависимых операций, а не фиктивный ACK.

## 6. Происхождение сообщений

Предпочтительный кандидат — custom message Pi с типом Artel, `message_id`, автором, задачей и видом сообщения в details, плюс читаемый конверт в content. SDK-эксперимент подтвердил корреляцию в событиях/истории и отсутствие human input hook, но provider payload всё равно имеет роль user, а details модели не передаются. Поэтому происхождение должно быть явно отражено в content; подпись не заменяет проверку полномочий. Окончательный выбор требует ещё TUI-проверки и recovery-эксперимента.

Сообщение от ревьюера не маскируется под владельца. Полномочия проверяет сервер, а не модель по надписи «от пользователя». Сырой текст не исполняется как extension/slash-команда: prompt-template/command expansion не включается для произвольного сообщения. Обращение к навыку — отдельное явное действие в разрешённом процессе.

Обычный ввод пользователя напрямую в Pi не копируется целиком в Artel по умолчанию и не превращается автоматически в структурированное разрешение. Участник сообщает связанные решения через предусмотренный инструмент или пользователь явно связывает сообщение с задачей. Ограничение полноты истории при работе вне Artel видно в продукте.

## 7. Инструменты агента

Названия ниже концептуальные, не утверждённые API:

- Получить свою задачу и её актуальные границы.
- Сообщить этап/блокер или предложить изменение плана.
- Отправить консультацию указанному разрешённому участнику.
- Создать вопрос владельцу с вариантами и рекомендацией.
- Передать результат/проверку с идентификатором кандидата и ссылкой на артефакт.
- Подтвердить получение конкретной версии поручения/решения.

Инструмент «задать вопрос» сохраняет вопрос и **сразу возвращает его ID и состояние pending**, а не удерживает вызов инструмента часами. Агент завершает текущий ход либо выполняет разрешённую независимую часть. Ответ приходит как коррелированное продолжение. Сохранённый pending нельзя представлять как уже полученное разрешение.

Сервер может запрещать недопустимый переход этапа, но агентное сообщение «тесты прошли» остаётся отчётом, пока нет требуемого источника доказательства. Запрос plan-only следующей задачи не превращается в разрешение implementation; область работы хранится явно.

## 8. Жизненный цикл и отказ

| Ситуация | Требуемое поведение |
|---|---|
| Reload расширения | Новая instance/generation, сверка незавершённых dispatch; без автоповтора старого intent |
| `/new`, `/fork`, новая история | Нет автоматического переноса активного поручения и полномочий из copied entries |
| Resume прежней истории | Аутентификация и сверка назначения/поколения, восстановление известных receipt, не догадка по cwd |
| Compaction | Correlation сохраняется вне summary; текст summary не доказательство исполнения/согласия |
| Отказ API | Уже разрешённая локальная работа может продолжаться; новые поручения/разрешения через Artel не принимаются |
| Потеря agterm | Если Pi-процесс жив, bridge не зависит от почты/окна; навигация недоступна |
| Истёк heartbeat | Связь stale, ответственность не передаётся другому writer автоматически |
| Отзыв доступа | Новые операции отклонены; сервер не обещает отменить произвольный уже исполняемый shell |
| Очередь изменена после fetch | Проверить ревизию при dispatch; не инъецировать отозванное/заменённое поручение |
| Отмена после intent | Запросить отмену/сверку, не заявлять, что ещё не началось; no atomic revoke после передачи |
| Локальный журнал переполнен/диск отказал | Явная ошибка долговечности, без ложных квитанций и новых зависимых запусков |

## 9. План технической проверки до продуктовой реализации

Это общая матрица технической проверки. По разрешению владельца выполнен [эксперимент №1](20261117-artel-v2-pi-experiment-01.md): SDK-инъекция, корреляция, input intercept, обычное переоткрытие и три SIGKILL-границы. Остальные блоки не закрыты; успешный SDK-прогон не подменяет TUI и серверный протокол.

### Окружение

Временный test project, fake Artel endpoint, отдельные private session/state directories и отдельная тестовая Pi-сессия. Не читать/ack почту работающих панелей, не изменять глобальные extensions/settings, не подключать реальные проектные credentials и не отправлять сообщения действующей команде.

Harness tests по возможности используют детерминированный тестовый провайдер. TUI smoke выполняется в отдельной тестовой панели, а не в текущем разработчике. Если нужен реальный провайдер, объём и выбранные параметры фиксируются отдельно, без автоматической смены модели/подписки.

### Проверяемые блоки

| Блок | Эксперимент | Ожидаемое доказательство |
|---|---|---|
| Registration | Startup/reload/new/resume/fork, одинаковые cwd и унаследованные AGTERM-переменные | Ни одна чужая/дочерняя сессия не принимает основное назначение |
| Injection | Custom vs user message, idle/busy, input intercept, ручной ввод в гонке, async error | Точно определены наблюдаемые границы и корреляция, не просто отсутствие exception |
| Durability | Новая пустая сессия, custom entries до диалога, выключенная persistence, аварии до/после каждого шага | Квитанции либо восстановимы, либо явно unknown; отсутствие необоснованного повторного prompt |
| Retry | Потеря ответа intent/receipt, duplicate event, повтор ключа с иным телом | Нет второго допуска/двойного решения; конфликты явные |
| Lifecycle | Reload, compaction, fork и восстановление session с копированными маркерами | Не потеряна привязка и не унаследованы чужие полномочия |
| Failure | API down/reconnect, ограниченный буфер, отказ/переполнение локального journal | Управляющие данные не теряются молча; активный Pi не блокируется из-за обычной телеметрии |
| Permissions | Отозванный credential, чужой project/task, старое поколение, попытка owner answer от агента | Сервер отклоняет мутации, попытки записаны без секретов |
| UI/terminal | Доставка и отображение в TUI; bridge без agterm mail; сравнение с headless event-path только для совместимости | Подтверждён основной TUI-сценарий, headless не выдаётся за его замену |

Crash-тест процесса не доказывает сохранность при потере питания. Это разные гарантии; отчёт обязан разделять их и фиксировать допущения ОС/файловой системы.

### Условие выхода

Краткий отчёт на точной версии Pi: какие API пригодны, где остаётся unknown, выбранный способ инъекции, журнал/ACK-порядок, подтверждённые recovery-сценарии и ограничения. После него можно фиксировать OpenAPI/extension contract и писать план первого продуктового среза.

Если достаточная корреляция недоступна через публичный API, не скрывать проблему за terminal scraping. Выбор: консервативное ручное восстановление, ограничение возможностей первой версии либо отдельное согласованное изменение Pi. Изменение харнеса/отказ от agterm не считается автоматически разрешённым исходом эксперимента.

## 10. Что ещё не выбрано

Режим уже согласован: очередь хранится в Artel, обычные сообщения передаются в свободный Pi, срочное вмешательство не входит в первый контракт. Открыты технические детали:
- Конкретная локальная авторизация/bootstrap и формат private receipt journal.
- Custom message или user message для инъекции — после экспериментального сравнения.
