# Продуктовый срез 4a — поручение владельца в одну Pi-сессию

Срез реализован по плану `docs/plans/20261119-artel-owner-pi-task-message.md`
(ветка `feature/artel-pi-delivery-02`, база `origin/main` `4bb9869`).
Это **не** обновление работающего экземпляра и не пилот: реальная установка,
обновление существующих сессий и пилот на рабочем проекте — отдельные решения.

## Проверенная связка

Production Qt (экран задачи, предупреждение до отправки) → owner HTTP
(`POST /v1/tasks/{id}/messages` с `instance_id` и `Idempotency-Key`) → SQLite
(транзакционная запись, проверка назначения и готовности) → delivery UDS
(общий Unix listener, отдельный delivery-токен) → привязанный writer в Pi
(kernel-блокировка unix-bind, CAS attach, single spend/verify, синхронный
transmit без `await` между idle-проверкой и `sendMessage`) → квитанция
`before_agent_start` (custom, точные details) → `observed` в истории задачи.

## Доказательства

- `python3 -B integrations/pi-observer/tests/delivery_pty.py --smoke` — настоящий
  `arteld` + настоящий Pi в PTY + детерминированный loopback-провайдер: отказ
  POST до attach и между attach/ready без записи; ровно один вызов провайдера на
  поручение; replay ключа без второго вызова; отказ для чужого проекта и чужого
  `instance_id`; `observed` в owner GET; второй writer получает отказ блокировки.
- `integrations/pi-observer/tests/delivery.test.ts` (27 unit) — потерянный attach
  под блокировкой, CAS-передача владения, отказ записи журнала после spend
  (право не достигает Pi), рестарт без повторной передачи с републикацией
  квитанции, round-trip максимально экранированных 8 КиБ, дублированный callback
  = один вызов, busy = ноль вызовов.
- `internal/store/delivery_test.go` (20 тестов) — миграция v1/v2→v3 и откат,
  единственный победитель у конкурирующих spend, close/archive блокируют
  необратимо и reopen/unarchive не возобновляют очередь, revoke до/после verify,
  квитанция после отзыва отклонена с сохранением `unknown`, потерянный ACK не
  понижает закоммиченный `observed`, отказ старого бинарника открыть v3.
- `./desktop/bin/test` — 35/35, включая повтор того же ключа при неизвестном
  исходе и отказ повтора в другую БД с сохранением черновика.
- Полный прогон `make lint test build` на каждой задаче: зелёный.

## Границы восстановления и отзыва

- `observed` означает только точное `before_agent_start` наблюдение; `unknown`
  никогда не вызывает автоматической повторной отправки.
- После отзыва впервые пришедшая квитанция отклоняется; уже сохранённый
  `observed` не понижается. Уже выданный вызов не обещаем отменить.
- Закрытие задачи/архив проекта запрещает будущий `verify` потраченных попыток;
  повторное открытие отметку не снимает.
- Power loss и откат данных сервера не считаются доказанным восстановлением;
  отсутствие локальной записи не отменяет серверный spend.
